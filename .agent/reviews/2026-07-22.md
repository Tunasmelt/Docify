## FEAT-003 — JWT auth middleware

- **INFO** — Algorithm confusion is closed in the implementation: `jwt.decode()` is called with hardcoded `algorithms=["ES256"]`; the token header is not used to select the algorithm. The signing key is resolved through `PyJWKClient` by token `kid`, then verified as ES256. An HS256 token cannot be accepted through this decode call merely by presenting JWKS public-key material.
- **WARNING** — `exp` is verified by PyJWT when the claim is present, but `exp` is not required. A correctly signed token without an `exp` claim can therefore pass. The existing expired-token test covers rejection of an expired claim, not the missing-expiry case.
- **WARNING** — The middleware does not validate `iss` against the expected Supabase project URL. A validly signed token from another issuer/project could be accepted if its signing key is available through the configured JWKS client. There is no issuer test.
- **WARNING** — Audience validation is explicitly disabled with `options={"verify_aud": False}`. Tests generate `aud: "authenticated"`, but the middleware has no expected audience and accepts any audience, or no audience at all. If the project contract requires Supabase’s `authenticated` audience, this is an untested acceptance gap.
- **INFO** — An unknown `kid` is resolved by `PyJWKClient.get_signing_key_from_jwt()`. Its `PyJWKClientError` is a PyJWT error and is caught by the `except jwt.PyJWTError` branch, producing a 401 rather than falling through to the protected route. The test fake always returns one key and does not exercise unknown-kid behavior, so this fail-closed property is source-derived rather than test-proven.
- **WARNING** — Unauthorized messages are not fully generic: missing/malformed Authorization, invalid-or-expired JWT, and missing `sub` receive different messages. They do not expose raw signature/JWKS details, but the distinction leaks which broad validation stage failed and is more specific than the contract’s generic “Missing or invalid JWT” meaning. The suite does not assert the error-message policy.
- **INFO** — Runtime inspection of Uvicorn output for unauthenticated `/protected` and `/health` requests showed only standard access/startup/shutdown lines. There is no application auth logger, and no observed runtime output contained the raw token, JWKS response, or key material. The static source likewise has no logging of those values.
- **WARNING** — Coverage is incomplete for the requested security boundaries. The current file contains 8 auth tests (the combined auth/health run had 10 tests total), covering expired `exp` but not missing `exp`, not `iss`, not wrong/missing `aud`, not algorithm-confusion rejection, not unknown/missing `kid`, and not clock-skew/leeway edges. The fake JWKS client ignores the token `kid`, so it cannot detect key-selection regressions.
- **INFO** — The complete test run passed 10 tests and skipped 14 migration tests due to unavailable local Postgres. The live-token history described in project documentation was not treated as independent proof of these untested claim and key-selection edges.
