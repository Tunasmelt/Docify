# Independent review: FEAT-004 — Docling parser service

Review date: 2026-07-23  
Scope: `apps/api/services/parser.py` and `apps/api/tests/test_parser.py`; read-only review.

## Findings

- **WARNING — Returned figure images retain live in-memory file objects.** A direct parse of `scanned.pdf` produced a `PIL.Image.Image` whose `fp` was an open `BytesIO` (`closed=False`). The parser also creates its input `BytesIO` without an explicit `close()`/`finally`. This is not an OS file-descriptor leak—the parser reads from memory—and closing a returned image inside `parse()` would invalidate the object FEAT-005 needs. However, image/resource ownership is implicit: callers must close each returned figure image after persistence, and retained `ParsedDocument` objects retain image memory. There is no parser-level cleanup or test asserting that ownership protocol, so large documents or many retained parses can build memory pressure.

- **INFO — Corrupt/truncated conversion errors are surfaced cleanly, with no guessed page.** The converter exception is wrapped as `ParseError`; the existing invalid-bytes test passes, and a manually truncated `clean_digital.pdf` also raised `ParseError`. Its `page_number` was `None`, which is accurate because Docling rejected the document before page provenance existed. Content-extraction failures use `prov.page_no`, so that page number is source-derived rather than guessed. Docling did emit its own internal traceback to stderr before the wrapper error during the truncated probe, but the error was not swallowed and the caller received `ParseError`.

- **WARNING — Post-conversion structural failures are not normalized to `ParseError`.** The `try` block covers only `converter.convert()` and per-element content extraction. `doc.iterate_items()`, `item.prov[0]`, and `prov.bbox.l/t/r/b` are outside those protected paths. If a malformed Docling result has missing provenance/bbox or iteration fails, a raw exception can escape instead of the `ParseError` contract FEAT-005 is expected to consume. No current fixture triggered this; this is an untested robustness boundary.

- **INFO — Bbox shape is consistent across the three supplied fixtures.** An audit of all parsed elements found 21 elements in `clean_digital.pdf`, 66 in `table_heavy.pdf`, and 2 in `scanned.pdf`; every bbox had four float values in `(x0, y0, x1, y1)` order, including all 29 tables and 19 captions. No malformed or `None` bbox was observed. The implementation maps Docling’s `l/t/r/b` fields consistently. The test suite only asserts bbox values on `clean_digital.pdf`, so table/scanned bbox coverage remains a test gap.

- **INFO — Scanned-PDF degradation is currently explicit and stable, not a silent parser crash.** OCR is disabled as documented for FEAT-017. Repeated parses of `scanned.pdf` consistently produced exactly two elements—one heading and one figure, both on page 1—with pages 2 and 3 producing zero elements. There is no suspicious-low-element-count signal or warning in the parser; that is intentionally unhandled until FEAT-017. The behavior was deterministic in this review, but it represents silent partial content loss by design.

- **WARNING — Captions can be silently dropped when provenance is absent.** The table-heavy fixture produced all 29 tables and all 19 caption elements; there is no required 1:1 table/caption relationship, and captions are retained as independent elements. However, the shared `if element_type is None or not item.prov: continue` branch drops a recognized caption whenever Docling supplies no provenance, without an error or marker. Thus captions are not silently dropped in the supplied fixture, but the parser has a silent-drop path for malformed/incomplete caption provenance and no association metadata for FEAT-005 to use.

- **WARNING — The seven parser tests do not cover empty or truncated PDFs.** `test_invalid_pdf_bytes_raises_parse_error` exercises a non-PDF byte string, not an empty file or a truncated but initially recognizable PDF. The manual truncated-input probe passed, but that behavior is not regression-tested. The tests also do not exercise post-conversion malformed provenance/bbox, figure cleanup, or bbox invariants on table/scanned fixtures. FEAT-005 therefore has only partial automated proof that `parse()` either returns structurally usable output or raises cleanly.

## Verification

The targeted fixture tests for tables, figures, and scanned degradation passed (`3 passed`); the invalid-bytes test passed (`1 passed`). The full parser suite was not allowed to complete concurrently because Docling fixture processing spawned ~1 GB workers; the targeted checks and direct sequential fixture audit completed successfully. No application code was modified during this review.

## FEAT-005 — chunker service

- **WARNING — The ~500-token budget is a character proxy, not model tokenization.** `_approx_token_count()` uses `len(text) // 4`; there is no tokenizer matching the eventual Voyage embedding model. This can materially undercount dense tables, code-like text, punctuation-heavy content, and non-English text. More importantly, a single oversized groupable element is never split, and tables/figures are always emitted as one chunk regardless of size. Synthetic probes produced one 2,100-character text chunk (approx. 525 proxy tokens) and one 10,001-character table chunk (approx. 2,500 proxy tokens). FEAT-006 will receive no size guard from this service, so an oversized table or dense text block can hit Voyage input limits or create inconsistent embedding behavior.

- **INFO — No table-row or heading boundary split was found.** Groupable elements are added whole and a table/figure flushes pending text before becoming its own chunk. Large tables are therefore not split across chunks at the row level; they are kept whole, even when oversized. The real fixture test produced 29 table chunks and verified one table source element per table chunk with intact markdown pipe content. No concrete boundary violation was observed.

- **WARNING — Tier-2 heuristic has unproven edge behavior despite a documented primary tiebreak.** The implementation sorts candidates by `(abs(element_index - caption_index), bbox_distance)`, so reading-order distance wins and physical distance breaks a reading-order tie. Synthetic probes confirmed that behavior, including a case where bbox proximity chooses the nearer candidate when reading distance ties. A fully equal tie silently selects the first candidate in `elements` order; that final tiebreak is implicit rather than documented or keyed by a stable element ID. Also, captions are processed sequentially and `claimed_targets` makes the first caption win a target, rather than solving multiple-caption assignment globally. The only Tier-2 tests are the six real `table_heavy.pdf` resolutions plus one synthetic orphan-caption case; there are no synthetic tests for equidistant candidates, conflicting reading-vs-position candidates, duplicate claimant captions, or fully equal ties.

- **WARNING — `chunk_index` is gap-free per run but not independently guaranteed stable across reparses.** The index is assigned from `len(chunks)` in emission order, so a single `ParsedDocument` always yields contiguous zero-based indices. That order is inherited directly from `ParsedDocument.elements` and the parser/Docling iteration order; the chunker does not canonicalize it by page, bbox, or stable element ID. Repeated chunking of the same in-memory parsed document is deterministic, but there is no test that parses the same file twice and compares chunk order/indices, and an upstream ordering change would renumber chunks.

- **INFO — Uncaptioned tables are structurally valid on the real fixture.** The 10/29 uncaptioned table chunks are emitted independently with table content, page numbers, source indices, `image=None`, `merged_caption_ids=[]`, and `association_method=None` (the documented “not applicable” value). Existing metadata and table-content tests cover these chunks; no missing required field or malformed standalone table was observed.

- **WARNING — Tier-2 coverage is predominantly fixture-specific.** `test_tier2_heuristic_resolves_all_six_remaining_captions_in_table_heavy` pins the six manually checked matches, and `test_tier2_heuristic_leaves_genuinely_unmatched_caption_standalone` covers only the no-candidate-page case. The remaining heuristic edge cases are not represented synthetically, so correctness beyond those six real examples is not established.

- **INFO — Association metadata is present on every emitted `Chunk`, with intentional `None` values.** The dataclass field defaults to `None`; text/heading/list chunks and genuinely uncaptioned table/figure chunks use `None`, explicit links use `explicit`, Tier-2 links use `heuristic`, and standalone unresolved captions use `unmatched`. Merged caption IDs are retained. No emitted chunk path was found where the field is absent, but the tests do not assert the allowed association value and field presence across every produced chunk.

### FEAT-005 verification

`apps/api/tests/test_chunker.py`: 10 passed in 108.46s. Synthetic probes also confirmed: no same-page candidate produces an `unmatched` caption chunk; reading-order ties resolve by bbox distance; fully equal ties resolve by source-list order; and oversized elements remain single chunks. No application code was modified during this review.

## FEAT-006 — Voyage embedder wrapper

- **WARNING — The input-count limit is enforced, but the 320,000-token limit is enforced only against a rough proxy.** `_batch_chunks()` correctly starts a new batch at 1,000 inputs and uses the stricter 280,000 proxy-token budget, so a synthetic 100-input case of roughly 4,000 proxy tokens per chunk split on the token dimension well before the input-count limit. However, text is estimated as `len(text) // 4` and images as pixels/560, not with Voyage's tokenizer. FEAT-005's 4,000-proxy-token ceiling can still be materially larger in real tokens, and `_REAL_MAX_TOTAL_TOKENS_PER_BATCH = 320_000` is not used for enforcement. A batch can therefore satisfy the local 280,000 estimate while exceeding Voyage's actual 320,000-token server limit. The implementation also places an individual input into a batch even if its estimate alone exceeds the safe budget; it relies on FEAT-005's ceiling to prevent that case.

- **INFO — Retry delegation is correctly single-layered.** The wrapper constructs the SDK client with `max_retries=3`, has no retry loop of its own, and maps transient exceptions only after they escape the SDK. Installed SDK source confirms `multimodal_embed()` wraps the call in tenacity and retries exactly `RateLimitError`, `ServiceUnavailableError`, and `Timeout`, with `stop_after_attempt(3)` and `reraise=True`. The tests patch the actual `voyageai.MultimodalEmbedding.create` call used by the SDK: transient-then-success made 3 underlying calls, exhaustion made 3 calls then raised `EmbedError`, and authentication failed after 1 call. No double-retry behavior was found.

- **INFO — Multimodal segment ordering is deterministic and tested.** `_chunk_to_input()` always appends non-empty text first and the image second. Image-only inputs contain only the image, with no empty text segment. The text-plus-image test asserts the exact list and object identity, so the wrapper applies one consistent ordering.

- **WARNING — Returned-vector cardinality is not validated, allowing silent loss.** On a successful SDK response, the wrapper blindly executes `vectors.extend(result.embeddings)` and never checks `len(result.embeddings) == len(batch)`. A synthetic client returning 4 vectors for 5 submitted chunks caused `embed()` to return 4 vectors without raising. A real rejected call does raise `EmbedError` and does not return an incomplete prefix, but any malformed/partial success response—or an inaccurate mock—can silently produce fewer vectors than chunks. There is also no batch/chunk context in the error if a call fails.

- **WARNING — Correspondence is preserved by current control flow but not fully asserted.** Batches are formed in input order, each SDK retry resubmits the same ordered `inputs`, and `vectors.extend()` preserves response order; the documented Voyage response is one embedding per input in request order. No reorder path was found. However, tests use fixed identical fake vectors for most multi-batch assertions and check only count, not a per-chunk marker-to-vector mapping; combined with the missing cardinality check, a response-order or partial-response regression could corrupt vector-to-chunk assignment silently.

- **INFO — Error mocks use the real Voyage exception classes but not realistic HTTP payloads.** `RateLimitError`, `AuthenticationError`, and `InvalidRequestError` are actual SDK classes, so retry classification and wrapper mapping are tested against the right types. Their test construction supplies only a message, while real SDK instances also carry `http_status`, `json_body`, headers/request ID, and parsed error data after HTTP response translation. Thus the tests accurately exercise post-translation retry behavior, but do not verify that real 429/invalid-request response bodies are translated into those exception classes or that response metadata is preserved in `EmbedError`.

- **INFO — Image ownership tests are substantive for the wrapper.** The post-embed test calls `image.load()` and reads `image.size`, which would fail for a closed PIL image; the separate patched `Image.Image.close` test observes calls across the embed operation and asserts none occurred. Together with the implementation passing the same image object through unchanged, these are not trivially passing assertions. They validate wrapper ownership, though the fake client does not exercise the SDK's real image serialization path.

### FEAT-006 verification

`apps/api/tests/test_embedder.py`: 16 passed, 1 opt-in real-Voyage test skipped. Synthetic probes confirmed token-dimension splitting, text-before-image ordering, deterministic tie behavior inherited from chunking, and the unhandled partial-response cardinality case. No application code was modified during this review.

## FEAT-007 — `POST /ingest` pipeline wiring

- **INFO — The storage-path double-prefix fix is complete for current storage call sites.** The route requires `uploads/{authenticated_user_id}/` before creating the document or scheduling work. The download path then strips exactly `uploads/` before calling `client.storage.from_("uploads").download(...)`, avoiding `uploads/uploads/...`. The only other application storage writer, `_upload_figures`, uses `client.storage.from_("figures")` with the bucket-relative path `{user_id}/{document_id}/{chunk_index}.png`; it does not repeat `figures/`. Test helpers and the e2e reader use the same bucket-relative convention. No equivalent reverse-prefix bug was found.

- **WARNING — Background-task failure recovery is not total and there is no timeout/dead-letter mechanism.** `run_ingest_pipeline()` catches ordinary stage exceptions, logs them, deletes chunks, and marks the document failed. But pipeline dependency construction (`get_service_role_client()`, `Parser()`, `Chunker()`, `Embedder()`) occurs before the `try`, so an initialization failure can escape with the row still `uploaded`. Inside the `except`, if `delete_chunks_for_document()` fails, `mark_failed()` is never reached; if `mark_failed()` itself fails, the row can remain `parsing` (or another prior status). A process kill, worker restart, or genuinely hung Docling/Voyage/Storage call likewise has no watchdog, lease, retry queue, or dead-letter path. FastAPI `BackgroundTasks` does not supply durable job recovery. The tests cover a handled embedder exception, not these recovery failures or a hang.

- **INFO — The chunks bulk-insert atomicity claim is valid for the current call.** `queries.insert_chunks()` sends the complete `rows` list in one `client.table("chunks").insert(rows).execute()` request; it does not loop over rows or issue per-row inserts. PostgREST maps a JSON-array insert to one PostgreSQL statement, and one PostgreSQL statement is atomic: a constraint error aborts the statement rather than committing a prefix. The pipeline also performs this insert only after parse/chunk/embed/figure-upload stages finish. This does not make previously uploaded figure objects transactional, and recovery after an ambiguous network failure still depends on the subsequent cleanup calls.

- **INFO — The documented orphan-storage scope is accurate.** `SCOPE.md` promises “no partial-ingest data left in `chunks`” and does not promise transactional Storage cleanup. The route can upload figure objects before a later chunk insert or status update fails; the implementation documents this as an accepted gap, and the feature notes identify it separately. No larger storage-cleanup promise was found in the scope text.

- **WARNING — Authorization ordering is correct on the public endpoint, but the nonexistent-path behavior is asynchronous rather than 403.** In `post_ingest`, the JWT is established by middleware, request validation completes, and the user-prefix check runs before MIME validation, service-client creation, document insertion, background scheduling, download, parsing, or embedding. A path belonging to another user gets the same immediate 403 regardless of whether that object exists, so the endpoint does not probe cross-user existence. A path with the caller’s valid prefix but no object is accepted with 202, then the background download fails and the document eventually becomes failed; it is not a 403. The pipeline function itself does not repeat the user-prefix check, so a future/internal caller that invokes `run_ingest_pipeline()` directly could bypass the route invariant; all current production wiring passes through the checked route.

- **INFO — The local fakes are structurally compatible with the current pipeline contracts.** `FakeParser` returns a real `ParsedDocument` containing real `ParsedElement`/`BBox` values; `FakeChunker` returns real `Chunk` objects with valid source indices/page lists; and `FakeEmbedder` returns 1024-float vectors with per-index values. The real local Supabase/Auth/Storage path is used rather than faked. The fake pipeline therefore exercises the actual status, figure-upload, row-building, and RLS wiring. It does not validate real Docling/Voyage serialization—that is delegated to the single gated e2e test—but no field-name/type mismatch was found in the fake shapes.

- **WARNING — The 72.7-second real run has not been checked against a configured production execution budget.** The repository contains no Render manifest, Gunicorn/Uvicorn timeout, reverse-proxy timeout, task deadline, or background-worker queue configuration. The only timeouts found are test helper/database connection timeouts. Render documents web responses as allowing up to 100 minutes ([official Render comparison](https://render.com/docs/render-vs-vercel-comparison)), but this work runs in FastAPI `BackgroundTasks` on the web service after the response and is not a durable Render background worker; the web-service response limit therefore does not establish a task execution guarantee. Render separately recommends background workers for long-running jobs ([official Render background-worker docs](https://render.com/docs/background-workers)) and documents a default 30-second graceful shutdown delay unless configured ([official Render blueprint reference](https://render.com/docs/blueprint-spec)). A 200-page document could plausibly exceed the observed 72.7-second 11-page run, and its survival/recovery behavior has not been validated against an actual Render deployment.
