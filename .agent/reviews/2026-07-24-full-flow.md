## 1. `user_id` trust chain, JWT → FEAT-011

**Trace:** `request.state.user_id` (FEAT-003 JWKS/ES256 middleware) → `routes/ingest.py`/`routes/documents.py` read it directly off `request.state` at every existing route (`user_id = request.state.user_id`, confirmed by grep — no route re-derives it another way) → passed explicitly into `Retriever.retrieve(question, document_ids, user_id, k)`.

**Confirmed live (grep, not restated):**
```
grep "Retriever|Generator|Verifier" routes/*.py main.py  → no matches
grep ".retrieve(|.generate(|.verify(" apps/api/**/*.py   → only test_retriever.py, test_generator.py, test_verifier.py
```
FEAT-009's self-audit finding ("zero production callers of `Retriever.retrieve()` exist yet") is **still accurate today**, and now extends identically to `Generator.generate()` and `Verifier.verify()` — neither has ever been called from `routes/` or `main.py`.

**New finding — the trust boundary is narrower than it might look:** `Generator.generate()` and `Verifier.verify()` don't just trust their caller's `user_id` the way `Retriever` does — they have **no `user_id` parameter or field at all**. `GeneratorChunk` carries no `user_id`. Once chunks leave `Retriever.retrieve()`, there is no tenant concept anywhere downstream — `Generator`/`Verifier` process whatever `GeneratorChunk` objects they're handed with zero awareness of who they belong to. This means:

- Tenant enforcement happens at **exactly one point** in the entire chain: `Retriever`'s two RPC functions' `WHERE c.user_id = match_user_id` clause (SQL-layer, verified independently in FEAT-009's audit).
- There is no defense-in-depth at the `Generator`/`Verifier` layer — by design (each service does one thing), but worth stating explicitly: **FEAT-012 is the entire safety net** for ensuring `Retriever.retrieve()` is always called with `request.state.user_id` and that its output is the *only* source of chunks ever handed to `Generator`/`Verifier`. A FEAT-012 bug that merges chunks from two different `retrieve()` calls, or calls `retrieve()` with a wrong/stale `user_id` once, would have nothing downstream to catch it — `Generator`/`Verifier` would process the resulting mixed-tenant chunks without any error or warning.

**Verdict:** No new code gap found (this is consistent with FEAT-009/010/011's own documented scope), but the concentration of trust into one single call is now stated precisely, not just implied. FEAT-012's `request.state.user_id` → `retrieve()` handoff is the single highest-value thing to get right and test adversarially when FEAT-012 is built.

## 2. Chunk field survival across all four representations

Traced a **real** chunk from a real ingested document through all four stages, printed live (not read from dataclass definitions alone). Ran twice — once against `table_heavy.pdf` (a `TABLE` chunk, `association_method="explicit"`) and once against `scanned.pdf` (a real `FIGURE` chunk with an actual image) to cover both branches.

### Field-presence table

| Field | `chunker.Chunk` | `chunks` table row | `retriever.RetrievedChunk` | `generator.GeneratorChunk` |
|---|---|---|---|---|
| `chunk_id` / row `id` | — (assigned by DB) | ✅ `id` (uuid, DB-generated) | ✅ `chunk_id` | ✅ `chunk_id` |
| `content` | ✅ `content` | ✅ `content` | ✅ `content` | ✅ `content` |
| `image` | ✅ `image` (`PIL.Image \| None`) | → `figure_path` (Storage path, **not raw bytes**) | ❌ **absent** (RPC functions never `SELECT figure_path`) | ✅ `image` (`bytes \| None`) — **only populated if the caller manually re-fetches it from Storage; nothing does this automatically** |
| `page_number(s)` | ✅ `page_numbers` (list) | ✅ `page_number` (singular, `min(page_numbers)`) | ✅ `page` (singular) | ✅ `page_number` (singular) |
| `element_type` | ✅ `element_type` (enum) | ✅ `element_type` (string) | ✅ `element_type` (string) | ✅ `element_type` (string) |
| `association_method` | ✅ `association_method` | ✅ (inside `metadata` JSONB, not a top-level column) | ❌ **absent** | ❌ **absent** |
| `document_name` | n/a | n/a (only `document_id`) | ✅ `document_name` (joined from `documents.filename`) | ✅ `document_name` |

**Real captured evidence (table chunk, `table_heavy.pdf`):**
```
STAGE 1 (Chunk):        element_type=TABLE, association_method='explicit', image=None
STAGE 2b (DB row):      figure_path=None, metadata={'association_method': 'explicit', ...}
STAGE 3 (RetrievedChunk): HAS image attribute: False | HAS association_method attribute: False
STAGE 4 (GeneratorChunk): image=None | HAS association_method attribute: False
```

**Real captured evidence (figure chunk, `scanned.pdf`):**
```
STAGE 1 (Chunk):        element_type=FIGURE, image=<PIL.Image size=(68, 69)>
STAGE 2b (DB row):      figure_path='{user_id}/{document_id}/0.png'
STAGE 3 (RetrievedChunk): image attribute absent (confirmed by design, not a bug)
STAGE 4 (GeneratorChunk): image=<bytes len=7957>  — reconstructed by MANUALLY downloading
                          from Storage via figure_path, simulating what FEAT-012 must build
```

**Findings:**
- `content`, `page_number`, `element_type`, `chunk_id`, `document_name` all survive intact end-to-end — no silent drops or renames among these.
- `image` survives structurally but requires an **explicit, currently-nonexistent-in-production** Storage round-trip between `RetrievedChunk` and `GeneratorChunk` (confirmed in item 3 below) — this is documented as FEAT-012's responsibility in `FEATURES.md`, and this trace confirms the documented plan actually works when executed for real, not just in theory.
- `association_method` is **silently dropped at the retrieval boundary** — persisted (inside `metadata` JSONB) but never `SELECT`ed by either RPC function, so it's unrecoverable from `RetrievedChunk` onward. **However:** grepped `FEATURES.md`/`ARCHITECTURE.md`/`services/generator.py`/`services/verifier.py` — `association_method` is never referenced as something FEAT-010/011 actually consume (`GeneratorChunk` has no such field, no system prompt references it). **This is a real but currently-harmless drop** — nothing today needs it past ingestion. Flagging it because if a future feature wants to surface "this citation came from a heuristically-matched caption" in the UI, it would need a migration to add `association_method` to the RPC `SELECT` list — not a blocker for FEAT-012, but worth knowing before someone goes looking for it downstream and can't find it.

## 3. Figure-image fetch: does anything already exist, or is it a build-from-scratch gap?

**Confirmed: build-from-scratch gap.** Grepped `routes/documents.py` and `db/queries.py` for every `figure_path`-related function:

- `list_figure_paths_for_document(client, document_id)` — bulk, whole-document, used only for cascade-delete cleanup in `DELETE /documents/{id}` (FEAT-008). Not scoped to specific `chunk_id`s, not usable for "give me this one retrieved chunk's image."
- `client.storage.from_("figures").remove(figure_paths)` — deletes figures, doesn't fetch them.

**Nothing exists that:**
1. Looks up `figure_path` for a specific set of `chunk_id`s (the shape FEAT-012 needs: "I retrieved these 5 chunks, which of them have a figure, and what's its path?").
2. Downloads figure bytes from Storage (`.storage.from_("figures").download(path)` is a raw Supabase SDK call — used directly, ad hoc, in this session's own test-only adapters for FEAT-010/011's real/gated tests, never wrapped into a reusable `db/queries.py` function).

FEAT-012 must build both. This was already implicitly known (FEAT-010/011's own acceptance criteria say "FEAT-012 must fetch each figure chunk's image from Storage via `figure_path`"), but this audit confirms there is genuinely nothing to reuse — FEAT-012 isn't at risk of missing an existing helper, because none exists.

## 6. End-to-end latency budget — real numbers, summed

Prior features never summed a worst-case `/query` latency. `test_retriever.py` itself reports **no real retrieval latency anywhere** (only a synthetic 0.4s-sleep concurrency proof and Voyage rate-limit pacing sleeps — confirmed by grep, neither is a real measurement). Measured retrieval live for this audit to close that gap.

| Stage | Real measured latency | Source |
|---|---|---|
| Retrieval (`Retriever.retrieve()`, real Voyage `embed_query` + real hybrid RPC search) | **401.9ms** | Measured live this audit, real `table_heavy.pdf` question |
| Generation (`Generator.generate()`, real Gemini 3.6 Flash) | **2148ms – 5885ms** (short → long/multi-citation answer) | FEAT-010's real 4-question quality test |
| Verification (`Verifier.verify_batch()`, real Gemini 3.5 Flash-Lite, up to `max_workers=8` concurrent) | **~1514ms – 2000ms** for up to 5–8 concurrent citations (tracks the single slowest call, not a sum) | FEAT-011's real 5-call concurrent batch test (1513.7ms total vs 5868.3ms would-be-sequential) |

**These three stages run strictly sequentially** (verification needs generation's citations; generation needs retrieval's chunks) — unlike the concurrency *within* each stage, they genuinely sum.

**Realistic worst-case `/query` total:** 402ms + 5885ms + ~2000ms ≈ **~8.3 seconds**, before any Next.js↔FastAPI network overhead or the conversation/message/citations DB writes FEAT-012 itself adds.

**Direct implication for FEAT-012's UX:** a bare synchronous request/response with no loading indicator would feel broken at 8+ seconds for the worst realistic case (and the *best* case — short answer, few citations — is still ~4 seconds: 402 + 2148 + ~1500). This is real evidence, not a guess, that FEAT-012 needs at minimum a loading/progress state, and streaming or staged status updates ("retrieving… generating… verifying…") are worth serious consideration rather than being an optional polish item.

**Update (2026-07-27, FEAT-009 rerank follow-up):** reranking (Voyage `rerank-2.5`, opt-in via `retrieve(rerank=True)`, default off — see `.agent/FEATURES.md`'s FEAT-009 entry) adds a real, separately-measured **mean 380.8ms** (min 354.8ms, max 408.4ms, n=4 real calls) on top of the 401.9ms retrieval figure above, i.e. retrieval+rerank together run **~782.7ms** rather than ~402ms when a caller opts in. This pushes the worst-case `/query` total from ~8.3s to **~8.68s** and the best-case from ~4.0s to **~4.4s** *only when rerank=True is passed* — the default (rerank not requested) is unaffected, still exactly the 401.9ms/8.3s/4.0s figures above. Not applied to any caller yet (opt-in, unused by default); flagging here so this budget doesn't go silently stale the day something does turn it on.

## 7. Full-chain multi-tenant isolation, chained live for the first time

FEAT-007/008/009 each proved isolation individually. This is the first time `retrieve() → generate() → verify()` was run **chained**, live, with two real users.

**Setup:** User A ingested real `table_heavy.pdf` (real Angola/HDI content, chunk_index confirmed). User B given a hand-crafted chunk with the **same embedding vector** as user A's real HDI chunk (a maximally adversarial setup — an orthogonal vector would never be retrieved regardless of scoping, so this proves scoping does the work, not distance) and distinctive canary content (`"LEAK-CANARY-B"`, a fabricated value `99.99`) in place of the real `4.42`.

**Ran full chain as user A, scoped only to user A's document:**
```
retrieve() results:        8 chunks, all document_name="table_heavy.pdf" — LEAK-CANARY-B present: False
generate() answer:         "In 2010, Angola's Human Development Index (HDI) value was 4.42 [1]."
                            LEAK-CANARY-B in GeneratorChunks sent to Gemini: False
                            LEAK-CANARY-B / 99.99 in the generated answer: False
verify() chunk checked:    table_heavy.pdf content — LEAK-CANARY-B present: False
                            verdict=supported, quote='Angola | - | - | 4.42 | 4.42 |'
OVERALL: any leak of user B's content into user A's chain: False
```
**Positive control:** user B retrieving their own document returned their own content correctly (1 chunk, contains `LEAK-CANARY-B`) — confirming the absence above is real scoping, not a broken query returning nothing for anyone.

**Verdict:** Isolation holds across the full chained pipeline, live, under an adversarial setup (identical embedding, same-topic-different-number content). No leak at any of the three stage handoffs.
