# 2026-07-23 Performance Review - FEAT-000 through FEAT-007

Scope: `apps/api/routes/`, `apps/api/services/`, `apps/api/db/`, `apps/api/models/`, `apps/api/middleware/`, `apps/api/migrations/`.

Validation performed:
- Reviewed ingest route, parser, chunker, embedder, DB query code, and e2e test.
- Could not replay the full real Voyage e2e locally because `VOYAGE_API_KEY` is unset in this shell.
- Profiled local parse/chunk stages on the three existing PDF fixtures with the real parser/chunker.
- Inspected batching tests and ran a synthetic 100 x ~4000-token batch split check.

## Findings

### [WARNING] Parse dominates fixture ingest time; no permanent per-stage timing exists

Must fix before serious performance claims or public demo sizing; fine to defer if the next step is still local feature work.

The current real e2e test records only total time around the HTTP POST (`apps/api/tests/e2e/test_ingest_e2e.py:45`). It does not record parse vs chunk vs embed vs Storage vs DB timing. The earlier documented run was 72.70s for `table_heavy.pdf`, 11 pages, 43 chunks, but the codebase cannot explain that number after the fact.

Local profiling without Voyage showed:

| Fixture | Elements | Chunks | Parse | Chunk | tracemalloc peak |
|---|---:|---:|---:|---:|---:|
| `clean_digital.pdf` | 21 | 3 | 7.64s | 0.001s | 27.8 MB |
| `table_heavy.pdf` | 66 | 43 | 86.55s | 0.002s | 51.4 MB |
| `scanned.pdf` | 2 | 2 | 3.87s | 0.000s | 26.5 MB |

On this machine, chunking is effectively free and Docling parse is the long pole. For a 200-page table-heavy document, linear extrapolation from `table_heavy.pdf` is not deployment-safe. It could be many minutes before embedding/storage/DB are even reached.

### [WARNING] Parser/converter and embedder/tokenizer are constructed per ingest

Must fix before public demo traffic if latency or memory spikes matter; fine to defer for one-at-a-time local usage.

`run_ingest_pipeline()` constructs `Parser()`, `Chunker()`, and `Embedder()` inside every background task unless injected (`apps/api/routes/ingest.py:219` through `apps/api/routes/ingest.py:221`). `Embedder` caches the Voyage tokenizer only on that instance (`apps/api/services/embedder.py:118` through `apps/api/services/embedder.py:121`), so default production flow re-resolves/reloads tokenizer state per document, not once per process.

Likewise, `Parser()` constructs a new Docling `DocumentConverter` per document (`apps/api/services/parser.py:106` through `apps/api/services/parser.py:108`). The profile output showed model-weight loading on parse. Even if Docling internally caches some model state, the application is not intentionally reusing the converter.

At current scale this is not a correctness bug, but it is avoidable latency and memory churn in the hottest path.

### [WARNING] The current FastAPI `BackgroundTasks` architecture can tie up web-worker resources for long ingests

Must fix before a credible public deployment; documented as Phase 5 and acceptable for local portfolio development.

`POST /ingest` returns 202, but the work still runs in the FastAPI web process as a background task (`apps/api/routes/ingest.py:173`). There is no queue, worker pool, timeout, backpressure, or per-user concurrency cap in app code.

Given the measured 86.55s parse time for one 11-page fixture locally, a handful of concurrent large PDFs could occupy the web service's limited CPU/memory for minutes. This combines with the already-documented Phase 5 background-task durability gap in `.agent/SCOPE.md`: a hung task is not killed/retried by app code, and a process restart loses in-flight work.

### [WARNING] Memory risk grows with full-document materialization and live PIL images

Fine to defer for the current fixtures; should be addressed or load-tested before allowing large/image-heavy PDFs.

The pipeline holds the whole PDF as bytes, the full `ParsedDocument`, all chunks, all vectors, and any live figure `PIL.Image` objects until the end of the pipeline. Images are closed in `finally` only after upload/insert work completes (`apps/api/routes/ingest.py:264` through `apps/api/routes/ingest.py:265`). This matches the parser ownership contract, but it means peak memory is per-document, not streamed.

The current fixtures are light: `table_heavy.pdf` produced no figure images and peaked at about 51.4 MB under `tracemalloc`; `scanned.pdf` produced one small image and peaked at about 26.5 MB. These numbers do not cover the risk case: 100+ pages with many rendered figures. A 2000x2000 RGB image is roughly 12 MB raw before Python/object overhead; dozens of open figure images can plausibly exceed free-tier memory even if the PDF file itself is small.

### [INFO] No app-code N+1 database query pattern found in the ingest path

No issue found.

The ingest pipeline performs a fixed number of DB calls per document: create document, mark parsing, mark parsed, mark embedded, bulk insert chunks, mark ready, plus cleanup/mark failed on failure. Chunk rows are built in memory and inserted in one call (`apps/api/db/queries.py:100` through `apps/api/db/queries.py:104`). There is no per-chunk insert loop and no per-element database fetch.

Figure uploads are per figure, not batched (`apps/api/routes/ingest.py:310` through `apps/api/routes/ingest.py:318`). That is a Storage N+1 path, not a DB N+1. Current real e2e fixture has zero figure chunks, so this cost is unmeasured.

### [INFO] Embedder batching logic works synthetically, but fixture-sized real ingest is single-batch

No immediate issue; coverage is adequate for logic, but the real e2e path does not exercise multi-batch behavior.

The `table_heavy.pdf` real e2e inserts 43 chunks, far below `MAX_INPUTS_PER_BATCH=1000` and below the token budget. Existing unit tests cover count-based and token-based splitting. A synthetic check with 100 chunks near the chunker's 4000-token ceiling split into two batches of 75 and 25, proving token budget binds before input count.

This means normal fixture e2e does not validate multiple real Voyage calls, but the unit-level batcher behavior is covered.

### [INFO] Database and Storage clients are constructed more often than necessary

Fine to defer at this scale.

`post_ingest()` constructs a service-role client to create the document (`apps/api/routes/ingest.py:162`), then the background pipeline constructs another one by default (`apps/api/routes/ingest.py:218`). That is redundant per request. It is not currently an N+1 or correctness problem, but a process-level client factory or passing the existing client into the task would reduce setup overhead.

### [INFO] Chunking itself is not a current performance concern

No issue found.

Real fixture profiling showed `Chunker.chunk()` at about 0-2 ms across all three fixtures. Its Tier-2 caption matching includes a nested scan over elements for explicit captions, but with current element counts it is negligible. Even at hundreds or low thousands of elements, Docling parse and external embedding calls will dominate first.
