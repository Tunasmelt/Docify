# FEAT-026 adversarial audit — 2026-07-25

Scope: independent re-examination of FEAT-026 (`GET /conversations`, `GET /conversations/{id}/messages`,
`figure_url` on `POST /query`), specifically requested because citation-marker correctness has already
produced two prior real bugs in this project (FEAT-010's grouped-bracket parsing loss, FEAT-011's
fabricated-quote verifier gap) that were only caught by adversarial re-examination, not by the original
build. Read-only investigation — no feature code changed by this audit. A throwaway probe test file
(`tests/test_zz_marker_audit_probe.py`) was written to generate the live evidence below, run against the
real local Supabase stack, then deleted; nothing from it is part of the permanent suite. All output below

## 1. The marker-persistence mechanism — priority item

### 1a. How were markers determined before this fix?

**Important scoping correction to the premise:** `GET /conversations/{id}/messages` is a **new** endpoint —
it did not exist prior to FEAT-026 (confirmed at the start of the original build: no route, no file, no
registration in `main.py`). So there is no shipped "before" behavior to have regressed — nobody has ever
called this endpoint in production or in a prior version of this codebase. There is, however, a real
"before" at the schema level: prior to this feature, the `citations` table had no `marker` column at all.
Confirmed via `git diff` against `HEAD` (every FEAT-026 file is uncommitted, so the working-tree diff is the
literal pre-fix vs. post-fix code, not a reconstruction):

```diff
--- a/apps/api/routes/query.py
+++ b/apps/api/routes/query.py
@@
         citations_to_persist.append(
             {
                 "chunk_id": chunk.chunk_id,
+                "marker": position,
                 "claim_span": claim_text,
```

Pre-fix, `POST /query`'s `citations_to_persist` payload — the dict handed to `create_query_turn`'s RPC —
never included `marker` at all, and the original `create_query_turn` function (`migrations/20260724_002_query_persistence_function.sql`, still on disk, unmodified, the literal pre-fix version) never inserted it:

```sql
insert into citations (
  message_id, chunk_id, user_id, claim_span, claim_start, claim_end,
  verdict, supporting_quote, verifier_model
)
```

No `marker` column, no `marker` value anywhere in the write path. So the honest answer to "how were markers
determined at read time" is: **there was no code that did this yet** — the gap was caught while designing
`GET /conversations/{id}/messages`, before a read-time reconstruction was ever written and shipped. This
audit cannot show you a live "old, broken" version of the endpoint returning wrong markers, because that
version was never committed or run. What it can show — and did (§1d) — is that the **only two ways** to
build the endpoint without the column both produce a real, demonstrable wrong answer, which is presumably
why the build session caught it before shipping either one:

- **Option A (naive):** sequentially renumber whatever citations survive the `unsupported` filter, in
  return order, starting at 1.
- **Option B:** use `chunks.chunk_index` or some other chunk-intrinsic ordering.

Both are wrong for the same underlying reason — neither one is "the position this citation's `[N]` occupied
in the *specific* answer text it was generated for," which is a per-message, per-generation-call fact with
no other source of truth once the citation's row exists in isolation from the other citations of that
message.

### 1b/1d. Concrete failure scenario + live proof (combined — the proof constructs the scenario)

Built a real message with two real chunks, two real citations, one `SUPPORTED` (kept) and one `UNSUPPORTED`
(dropped) — the exact shape `_strip_dropped_markers` and the audit-trail persistence comment both describe,
run through the real `POST /query` endpoint (real DB writes, only Retriever/Generator/Verifier faked, same
discipline as the existing test suite):

- Generator's raw answer: `"First claim, unsupported [1]. Second claim, supported [2]."`, `cited_indices=[1,2]`
- Verifier: position 1 (chunk1) → `UNSUPPORTED`, position 2 (chunk2) → `SUPPORTED`

**Real captured output:**

```
=== STORED messages.content (post-strip) ===
'First claim, unsupported. Second claim, supported [2].'

=== STORED citations rows (both kept and dropped) ===
[
  { "marker": 1, "chunk_id": "4428271a-...", "verdict": "unsupported" },
  { "marker": 2, "chunk_id": "5477d41c-...", "verdict": "supported" }
]

=== NAIVE re-derivation (sequential renumber of KEPT-ONLY citations,
     matching what /query itself returns to the client) ===
{ "5477d41c-...": 1 }      <-- WRONG: stored content says "[2]", not "[1]"

=== GET /conversations/{id}/messages RESPONSE (real endpoint) ===
"citations": [{ "marker": 2, "chunk_id": "5477d41c-...", ... }]   <-- correct

=== VERDICT ===
stored content text: 'First claim, unsupported. Second claim, supported [2].'
real marker returned by GET /conversations/.../messages for chunk2: 2
naive kept-only renumbering would have returned: 1
MISMATCH: True
```

This is the concrete mechanism, with real IDs: whenever an earlier-positioned citation is dropped as
unsupported, any read-time renumbering scheme disagrees with the literal `[N]` text still sitting in
`messages.content` for every citation after the gap. The shipped endpoint (`routes/conversations.py`'s
`_citation_response`, `marker=row["marker"]`) reads the persisted column directly and never renumbers
anything — confirmed by reading the actual shipped code, not just the migration comment:

```python
def _citation_response(client, row: dict) -> CitationResponse:
    ...
    return CitationResponse(
        marker=row["marker"],   # <-- straight from the DB column, no enumerate() anywhere in this file
```

### 1c. What was actually persisted

Two real files, both applied to the local stack:

- `migrations/20260725_001_citation_marker_column.sql`: `alter table citations add column marker int not null default 0;` (default dropped after backfill).
- `migrations/20260725_002_query_persistence_function_marker.sql`: `create_query_turn` re-created with `marker` added to both the `insert into citations (...)` column list and the `values (..., (v_citation ->> 'marker')::int, ...)` tuple.

Persisting at write time closes the gap because `marker` is captured at the one moment it's unambiguous —
inside the same `for position, verdict in zip(verify_positions, verdicts, ...)` loop in `routes/query.py`
that already knows `position` (the literal `[N]` the chunk was generated against). Once that loop exits,
the information "which `[N]` was this" cannot be recovered from anything else stored about the citation —
not `chunk_id` (a chunk can be cited at different positions in different messages), not verdict order, not
any other column.

### 1e. Pre-existing dev data — backward-incorrect and unrecoverable?

Checked the real local dev DB directly:

```
citations with marker=0 (backfilled, pre-migration rows): 0
total citations rows: 0
conversations: 0   messages: 0   citations: 0   documents: 0
```

**The local dev DB is currently empty.** Every test fixture (`user_a`/`user_b`) deletes its user at
teardown, and Postgres FK cascade removes that user's conversations/messages/citations along with it — so
no citation rows from any prior FEAT-012 through FEAT-025 testing session survive between runs. There is
no `marker=0` backfilled row sitting in this database right now that `GET /conversations/{id}/messages`
could silently mis-report. **Not a real concern for this project's data**, for two independent reasons: (1)
empirically, there is nothing to be wrong about right now, and (2) even if there had been, this is
established local dev/test data — the project's own standing discipline (never production, local stack
only) already treats this as disposable. If this endpoint is ever pointed at a database with real
pre-migration citation rows, those specific rows would report `marker=0` (visibly wrong/sentinel, not
silently plausible-looking) rather than a wrong-but-plausible number — worth knowing, not worth blocking on,
since no such database exists yet.

**Verdict on item 1:** The mechanism is real and precisely as described in the original summary, the schema
fix is correctly targeted at the actual source of truth, and the live reproduction confirms the exact
failure mode the migration's own comment predicted. The one correction to the original framing: this was
caught during design of a new endpoint, not fixed as a regression in previously-shipped behavior — worth
being precise about since "the marker-persistence gap fixed" could be misread as implying a shipped bug
existed and was silently returning wrong data at some point. It didn't; nothing ever called the naive path
in production.

## 3. `figure_url` on `POST /query`

### 3a. Actual expiry/scope, cross-checked against real docs

Exact code (`services/figure_fetcher.py`):

```python
FIGURE_URL_EXPIRY_SECONDS = 600

def signed_figure_url(client, figure_path: str) -> str | None:
    try:
        result = client.storage.from_("figures").create_signed_url(figure_path, FIGURE_URL_EXPIRY_SECONDS)
        return result.get("signedURL")
    except Exception:
        ...
        return None
```

Cross-checked against Supabase's own current docs (`search_docs`, not assumed from memory): the JS reference
examples use 60s and 3600s expiries interchangeably with no stated recommended default — `expiresIn` is
fully caller-determined, no server-side cap or guideline being contradicted by 600s. Docs also confirm the
scope model directly relevant here: a signed URL's signature is **bound to the specific object path**
(demonstrated live below) and grants access to **anyone holding the URL string** for its lifetime (bearer
token, not tied to the original requester's identity) — this is inherent to how Storage signed URLs work,
not a project-specific gap, and matches `.agent/api-docs/supabase-storage-py.md`'s own stated reasoning.

Decoded a real issued token's JWT payload from a live response: `"iat":1784984896,"exp":1784985496` — exactly
600 seconds, confirming the code's stated expiry matches what's actually issued, not just what the constant
claims.

**New evidence gathered by this audit (path-binding, not previously verified):** tampering with the object
path inside a real signed URL, keeping the same signature/token, real HTTP request:

```
tampering the object path in the same signed URL -> status 400
```

Confirms the signature is genuinely path-bound — a leaked/logged URL for one figure cannot be edited to
access a different object in the same bucket.

### 3b. Omit vs. null — real JSON, both a figure and non-figure citation in one response

```json
"citations": [
  {"marker":1, ..., "element_type":"text", "verdict":"supported", "supporting_quote":"plain text content"},
  {"marker":2, ..., "element_type":"figure", "verdict":"supported", "figure_url":"http://127.0.0.1:54321/storage/v1/object/sign/figures/.../0.png?token=..."}
]
```

```
text citation keys:   ['chunk_id', 'document_id', 'document_name', 'element_type', 'marker', 'page_number', 'snippet', 'supporting_quote', 'verdict']
figure citation keys: ['chunk_id', 'document_id', 'document_name', 'element_type', 'figure_url', 'marker', 'page_number', 'snippet', 'verdict']
```

`figure_url` is genuinely absent from the text citation's key set — checked against the raw JSON string, not
just the parsed dict (rules out a serialization layer silently reintroducing `null`). Confirms
`response_model_exclude_none=True` on the route decorator is doing its job for real requests, not just in
the model definition.

### 3c. Actually fetchable, correct image

```
fetched http://127.0.0.1:54321/storage/v1/object/sign/figures/.../0.png?token=... -> status 200, bytes match: True
```

Fetched over real HTTP, bytes compared byte-for-byte against the real uploaded PNG. Confirmed for both the
live `/query` response and, separately, the same figure read back later via `GET /conversations/{id}/messages`
(the permanent suite's own `test_get_conversation_messages_figure_citation_has_a_real_fetchable_signed_url`,

**Verdict on item 3:** All three sub-items hold, with one net-new piece of evidence this audit added
(path-binding under tampering) that the original build didn't specifically check.

## 4. Regression confirmation — `GeneratorChunk` and `documents.py` changes

Neither file was in the original task brief's file list. Read the real diffs (`git diff`, both files
entirely uncommitted so this is the literal before/after, not a reconstruction):

**`services/generator.py`** — one new optional dataclass field, purely additive:
```diff
     image: bytes | None = None
+    figure_path: str | None = None  # Storage object path; only meaningful when element_type == "figure"
```
Directly required by the task brief's own item 2 ("**Reuse** figure_fetcher.py's existing chunk-to-figure
resolution rather than adding a second lookup path") — `GeneratorChunk` had nowhere to carry the already-resolved
`figure_path` through to `routes/query.py` before this field existed; without it, reuse wasn't mechanically
possible and a second `chunks.select("figure_path")` lookup would have been the only alternative (the exact
duplication the brief said not to add). **In scope, not creep** — it's the literal mechanism the brief asked for.

**`routes/documents.py`** — pure mechanical extraction, zero behavior change:
```diff
-def _encode_cursor(created_at: str) -> str:
-    return base64.urlsafe_b64encode(created_at.encode()).decode()
-def _decode_cursor(cursor: str) -> str:
-    return base64.urlsafe_b64decode(cursor.encode()).decode()
+from routes._pagination import decode_cursor, encode_cursor
```
Same function bodies moved verbatim into `routes/_pagination.py`, call sites updated one-for-one
(`_encode_cursor` → `encode_cursor`, `_decode_cursor` → `decode_cursor`), nothing else touched. This one is
technically beyond the brief's literal text (the brief didn't explicitly ask for a shared pagination module),
but it's a direct, minimal consequence of the brief's own instruction to match "the existing documents-list
pattern from FEAT-008" for the new conversations list — building that pattern twice, verbatim, in two files
would have been the duplication this project's established discipline (`figure_fetcher.py`'s single
chunk-to-figure resolution, cited approvingly in the brief itself) already argues against. Confirmed
zero behavior change: all 9 `test_documents.py` tests pass unchanged (re-confirmed in the full-suite run
below), and the diff shows no logic changes, only a relocation.

**Full-suite regression check, fresh run with the live stack up (not the earlier run that hit a stopped
Docker Desktop and skipped 88 tests):**
```
========== 209 passed, 12 skipped, 470 warnings in 670.85s (0:11:10) ==========
```
12 skips are the e2e tests requiring live external API calls (`test_ingest_e2e.py`, `test_query_e2e.py`),
unrelated to either changed file. Zero failures.

**Verdict on item 4:** Both changes are in scope, both are minimal, and the regression check that backs
"209 passed, 0 failed" is now a genuine live result (the number in the original summary was accurate, but
