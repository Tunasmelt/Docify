## §Anti-patterns

Things tried and failed, or explicitly rejected during design. Do not retry without human confirmation.

### 2026-07-22 [claude-code] — CLIP-style dual-tower embeddings
**Context:** During v1 strategy selection, considered CLIP-style multimodal embeddings (separate text and image encoders).
**Why rejected:** Modality gap — image embeddings cluster near other image embeddings, text near text. Cross-modal retrieval (text query → image match) is degraded. Voyage's unified single-encoder architecture eliminates this. Do not swap to CLIP-family without solving the modality gap first.

### 2026-07-22 [claude-code] — Vercel serverless for the Docling backend
**Context:** User asked whether Python backend could run as Vercel serverless functions.
**Why rejected:** (1) Vercel serverless function size cap of 250MB is smaller than PyTorch + Docling. (2) 10-30s cold starts on first invocation kill UX. (3) Default 15s timeout too short for multi-page parse. Do not attempt to move FastAPI to Vercel serverless. If Render becomes a problem, use Railway or Fly.io — not Vercel.
**Update 2026-08-01 [claude-code]:** Reason (1) is now moot — FEAT-027 removed Docling/PyTorch entirely (pdfplumber's import cost is ~17MB, not 423MB). Reasons (2) and (3) are unrelated to the parsing library and still apply; the conclusion (don't move to Vercel serverless) still stands.

### 2026-07-22 [claude-code] — Application-level tenant filtering as primary defense
**Context:** Considered relying on app-level `WHERE user_id = ?` alone for multi-tenancy.
**Why rejected:** Every route becomes a potential leak surface. RLS at Postgres is the primary defense. App-level user_id filters remain for clarity/testability but the DB is the enforcement point. Never bypass RLS with service-role for a user-facing read path.
**Update 2026-10-06 [claude-code]:** This is not how the system was built. FastAPI uses the service-role client for every user-facing read and write (`db/client.py`), so RLS does not apply on that path and the explicit `user_id` filter in each query/RPC *is* the tenant boundary there. RLS protects only direct browser→Supabase access. Docs were corrected to say so (ARCHITECTURE.md §Multi-tenancy, SCHEMA.md). Moving FastAPI's user-facing reads onto a per-request, JWT-scoped client so RLS applies again is a possible future hardening, not current behavior.

### 2026-07-22 [claude-code] — Validating a security mechanism using a token forged by that same mechanism
**Context:** FEAT-003 (JWT auth middleware) was first built and "verified live" by self-signing an HS256 token with `SUPABASE_JWT_SECRET` and confirming the middleware accepted it. It did — because the verification code and the test both used the identical secret and algorithm, so the check could only ever pass. It never touched a real Supabase-issued token. When challenged to test against an actual login-issued JWT, that token turned out to be ES256 (Supabase's asymmetric signing-keys scheme, verified via JWKS) — completely incompatible with the HS256-shared-secret implementation, which had been sitting in `main` as "complete" and committed (`f5cd00f`).
**Why rejected:** Never treat "I forged a credential and my own code accepted it" as verification of anything except that the forging and the checking agree with each other — that's circular by construction. Never validate a security mechanism using a token forged by that same mechanism; get a token from the actual issuing system (a real login, a real signup, a real third-party auth flow) before calling any auth code "verified." This generalizes beyond JWTs — the same trap applies to webhook signature verification, API key checks, or any place where "I can produce output my own code accepts" is being mistaken for "my code correctly implements someone else's spec."

### 2026-07-22 [claude-code] — Docling default pipeline options
**Context:** FEAT-004 (Docling parser service). Docling's default pipeline downloads RapidOCR models on first use even when parsing fully-digital PDFs — must explicitly set `do_ocr=False` to stay in scope and avoid the unexpected download. Separately, `generate_picture_images` defaults to a setting that silently makes every figure element's image `None` with no error — must explicitly set `generate_picture_images=True` or figure extraction appears to work (elements exist) while actually producing no usable image data.

Kept as historical record — the general lesson (silent-failure-shaped library defaults need explicit overrides, not trust) still applies to whatever library is in use.

### 2026-07-23 [claude-code] — Docling prints its own traceback to stderr on conversion failure
**Context:** FEAT-004 Codex review. When `converter.convert()` fails (e.g. against a truncated/corrupt PDF), Docling/pypdfium2 print their own internal traceback to stderr *before* `Parser.parse()`'s `except Exception` catches it and re-raises as `ParseError`. ### 2026-07-23 [claude-code] — Chunker's Tier-2 caption matching is greedy, not globally optimal
**Context:** FEAT-005 (chunker service). `_resolve_tier2_captions()` processes captions in document order; a table/figure claimed via `claimed_targets` is unavailable to every caption processed after it. If two orphaned captions could both plausibly match the same single unclaimed table, whichever caption is encountered first in the document wins it — the second is left unmatched (a standalone `"unmatched"` chunk) even if, with full knowledge of both captions, it would have been the better fit for that table and the first caption would have been better left unmatched (or matched to a different table it also has a claim on).
**Why rejected (verdict: acceptable simplification, not a bug — revisit only with real evidence):** A globally optimal assignment (e.g. bipartite matching over all orphaned captions vs. all unclaimed targets on a page) is meaningfully more complex for a scenario that's rare in practice — most pages have at most one orphaned caption near at most one uncaptioned table. Measured on `table_heavy.pdf` (the only real multi-caption-per-page data available so far): 0 instances of two orphaned captions competing for one target. Do not build the globally-optimal version speculatively. Revisit only if a real document is found where greedy-first-wins produces a visibly wrong pairing (verified `test_tier2_first_caption_wins_when_two_captions_compete_for_one_target` documents and locks in today's greedy behavior as a regression test, not an endorsement that it's the best possible answer).

### 2026-07-23 [claude-code] — "No current caller violates an invariant" is not "the invariant is enforced"
**Context:** FEAT-007 Codex review of `routes/ingest.py`. `run_ingest_pipeline()`'s correctness depends on `storage_path` actually belonging to `user_id` — but that was only ever checked by `post_ingest()`, its one caller, before scheduling the background task. The pipeline function itself trusted the caller unconditionally. Nothing was *currently* broken — the only caller in the codebase always checked first — but that's a fact about today's call graph, not a property of the function. The same review also caught two adjacent instances of the identical shape: dependency construction (`get_service_role_client()`, `Parser()`, `Chunker()`, `Embedder()`) happened before the function's own `try` block, so a construction failure had no handler to reach — again, "works today" because construction happens to succeed today, not because failure was handled. Fixed by moving the invariant check and dependency construction inside `run_ingest_pipeline()`'s own `try`, with a dedicated `test_run_ingest_pipeline_refuses_mismatched_user_id_and_storage_path` that calls the function directly, bypassing the route entirely, to prove the function — not its caller — enforces the precondition.
**Why rejected (verdict: real gap, generalizes beyond this instance):** This project has now found this exact shape of gap more than once (see FEAT-003's circular-JWT-verification entry above — a different flavor of "the check technically passed" masking "the check doesn't actually prove what it claims to"). The general lesson: when reviewing or writing a function whose correctness depends on a precondition, checking "does every current caller uphold it" is necessary but not sufficient — ask "does the function itself refuse to proceed if it doesn't hold," independent of who's calling it or how many callers exist today. This matters most for background/async entry points and anything with more than one caller, where the "just check at the call site" instinct is easiest to reach for and easiest for a future second caller to silently violate. Apply this lens proactively in future reviews, not just when Codex happens to flag it.

### 2026-07-23 [claude-code] — `startswith()` is not a safe authorization boundary for path-like input
**Context:** A self-audit (run proactively, ahead of a separate Codex security/perf review) found `routes/ingest.py`'s `storage_path` ownership check — `storage_path.startswith(f"uploads/{user_id}/")` — was a genuine, confirmed-exploitable path traversal, not a theoretical concern. `"uploads/{attacker}/../{victim}/file.pdf"` passes that check (a literal string comparison has no concept of ".." semantics), and Supabase Storage's own server resolves the ".." before fetching the object — proven via both the storage3 SDK and raw HTTP directly against the real local Storage stack, returning the victim's actual file content through the app's privileged service-role client (which bypasses RLS entirely). The first fix attempt — reject any raw ".." path segment, require `posixpath.normpath(path) == path` — looked reasonable and matches the standard advice for this class of bug, but was **also** proven exploitable by the same live-testing discipline: a percent-encoded variant, `"uploads/{attacker}/%2e%2e%2f{victim}/file.pdf"`, contains no literal ".." segment and is already normpath-canonical (`posixpath` doesn't decode URL encoding), yet still resolved to the victim's file — some layer in the request chain (most likely the Storage server itself decoding the request URI's path component, which is standard, spec-compliant HTTP behavior per RFC 3986's definition of `%2e%2e` as equivalent to `..`) reversed the encoding before our check ever saw it. The fix that actually held up under live re-testing: stop trying to blacklist spellings of ".." (literal, encoded, double-encoded, and whatever comes next) and instead whitelist the allowed character set for the untrusted portion of the path (`^[A-Za-z0-9._-]+$`, no slash — real or encoded — permitted at all), checked against a prefix built entirely from trusted, server-side data (the JWT's own `user_id`, never client input).
**Why rejected (verdict: real, distinct lesson from the two "invariant not enforced" findings above):** Those findings were about *whether* a check runs at all (a check existed and was correct, just only in one of two places it needed to be). This is different in kind: the check ran in the right place every time, and was still wrong, because a bare prefix/substring comparison on a path-like string is not a security boundary — path resolution happens in a different, later layer (the filesystem, an HTTP server's URI decoding, a storage backend) that a purely textual check cannot see or agree with in advance. General lesson: for any input that will later be interpreted as a path (or URL, or any other string with its own resolution/decoding semantics), validate with a **whitelist of what's structurally impossible to misuse**, not a blacklist of known-dangerous patterns — and prove the fix against the real downstream resolver empirically (as done here, twice, since the first "obviously correct" fix wasn't), not by inspection of the validation code alone.

### 2026-07-27 [claude-code] — A synchronous call inside an `async def` SSE generator silently defeats streaming, and neither raw httpx nor FastAPI's `TestClient` reliably catch it
**Context:** FEAT-016 (`POST /query/stream`). `_stream_query_events()` yields an SSE `verifying` event, then called `Verifier.verify_batch()` — synchronous, blocking on `ThreadPoolExecutor.result()` — directly, with no `await`. This froze the asyncio event loop for the call's entire real duration (~8s, real Gemini verification calls). The observable symptom: the client received the `verifying` event and the following `citations-resolved` event at the **identical timestamp**, instead of with the real multi-second gap between them the whole point of a separate event was to surface. Two layers of tests were run against this and both passed anyway: a raw `httpx.Client.stream()` script, and pytest against FastAPI's `TestClient` (also httpx-based) — in both cases the client's own read/buffering behavior happened to coalesce the frames the same way the bug did, so nothing looked wrong. Only a real Playwright browser session against the real running dev server (`next dev` + `uvicorn`, no test harness in between) — sampling the DOM over time and, once that was ambiguous, adding a temporary client-side `console.log(performance.now())` per SSE event — made the simultaneous-arrival timestamps directly observable.
**Why this matters (verdict: real, generalizes beyond this one call site):** An `async def` generator that calls blocking code without `await`ing it in a thread doesn't just "run slower" — it can silently prevent the ASGI server from flushing bytes it already handed to `send()` moments earlier, because uvicorn needs the event loop to actually get scheduled to do that flush, and a long synchronous call inside the same coroutine starves it. This is invisible to anything that measures *content correctness* (the final answer/citations were always right) or even *total latency* (the numbers looked plausible) — it only shows up as a *timing/ordering* defect between two events that are supposed to be temporally separate, which is exactly the shape neither a unit test asserting on parsed event data nor a manual latency stopwatch is built to catch. httpx-based clients (raw or via `TestClient`) are not a reliable oracle for this class of bug — their own internal buffering can mask the exact symptom a real browser exposes. **Fix pattern:** wrap every synchronous/blocking call inside an async SSE (or any async streaming) generator in `asyncio.to_thread(...)`, not just the "slow" one — retrieval, verification, DB persistence, signed-URL generation were all wrapped in `routes/query.py`'s `_stream_query_events()`, not only `verify_batch()`. **When writing or reviewing any new async streaming endpoint, verify inter-event timing with a real browser (or at minimum a raw socket read with per-byte/per-chunk timestamps), not just a test-client-parsed event sequence** — the sequence being *correct* does not prove the *timing* between events is real.

### 2026-07-31 [claude-code] — Vectors from two different embedding providers are NOT comparable via cosine similarity, even at matching dimensionality — STANDING ANTI-PATTERN, not a one-off caveat
**Context:** `services/embedder.py`'s Voyage-embedding-fallback feature (Gemini `gemini-embedding-2` covers a batch when Voyage's own retries are exhausted, matching this account's real 3 RPM ceiling documented above). Both providers' vectors are `vector(1024)` — same column, same dimension count — but they are points in two different, unrelated embedding spaces produced by two different models. A `<=>` (cosine distance) comparison between a Voyage-space vector and a Gemini-space vector is not meaningless in the sense of erroring — it will return a real float that LOOKS like a valid distance — it is meaningless in the sense of not measuring semantic similarity at all. This is the dangerous shape of bug: no crash, no error, just silently wrong retrieval ranking that would be very hard to notice without specifically testing for it.
**The fix pattern, if you're adding a second embedding provider (fallback, migration, A/B test, or anything else) to ANY vector column:** track which provider produced each stored vector (`chunks.embedding_provider`, `.agent/SCHEMA.md`), never compare across that boundary, and only fuse across providers via **rank**, not raw score — `services/retriever.py`'s `_reciprocal_rank_fusion()` was generalized to accept N independent ranked lists (one per provider partition, run via `match_chunks_by_vector`'s `match_provider` filter) specifically because RRF only ever consumes each list's own internal rank order, never a cross-list score comparison — that's what makes fusing across incomparable spaces safe where fusing on raw distance would not be.
**Do not, under any circumstance:** query with one provider's embedding and compare it against another provider's stored vectors "just to see if it's close enough" — there is no meaningful threshold, and a result that happens to look plausible is not evidence it's correct.

### 2026-08-02 [claude-code] — A fallback provider's own real limits must be independently verified, never inherited from the primary provider's validation — STANDING ANTI-PATTERN, confirmed real not hypothetical
**Context:** `services/embedder.py`'s Voyage→Gemini fallback (2026-07-31) was built and shipped with the batch it hands to Gemini sized ONLY against Voyage's own real limits (`MAX_INPUTS_PER_BATCH=1,000`, `_SAFE_TOTAL_TOKENS_PER_BATCH=300,000`, `chunker.py`'s `MAX_CHUNK_TOKENS=4,000` derived against Voyage's real 32,000-token input limit) — never re-validated against Gemini's own, different, real limits. This was an *unstated assumption* for two days before being checked. When actually checked live (2026-08-02): Gemini's real per-input limit is 8,192 tokens (4x tighter than Voyage's 32,000) and its real per-batch request cap is exactly 100 (10x tighter than Voyage's 1,000, confirmed at the exact boundary — 100 succeeds, 101 fails). **The batch-size gap was not theoretical — it was a real, live-confirmed bug:** any Voyage batch above 100 chunks that fell back to Gemini would have hard-failed the entire fallback outright (`400 INVALID_ARGUMENT`), even though Gemini could handle the same chunks fine once correctly re-batched — the exact scenario "if Gemini's limits are tighter" was written to anticipate, proven true on the first real check. Separately, Gemini's real per-input failure mode on the token-limit side is WORSE than a clean rejection: it silently truncates with no error at all (proven live: a 60%-over-limit real input embedded successfully, cosine ≈0.999999 against an independently-embedded truncated-equivalent prefix of the same text).
**Why this generalizes, not just to this one fallback:** any code that constructs a request/batch sized against Provider A's real, verified limits, then hands that SAME already-sized artifact to Provider B (a fallback, a migration target, an A/B alternative, a multi-provider abstraction) without separately verifying B's real limits, is making an unstated, unverified assumption that the two providers' constraints match closely enough not to matter. They frequently don't, and the gap is not always a matching failure mode — one provider might reject cleanly where the other truncates silently, which is strictly worse (no error to catch, no log to grep, just quietly degraded output). **Fix pattern:** any multi-provider code path needs each provider's own real limits checked independently (empirically — real API calls, not just reading docs, see the next entry) and its own sizing/batching logic sized against ITS real limits, not inherited from whichever provider happened to be "the primary one" the original sizing logic was built for.
**Related, narrower lesson from the same investigation:** even a provider's own official documentation can describe the wrong endpoint's behavior. Google's image-understanding docs describe a size-dependent tiled token formula (up to ~1,548 tokens for a 960x540 image) — real, but for a GENERATION model, not the `gemini-embedding-2` endpoint this project actually calls, which costs a flat, constant 258 tokens per image regardless of size (confirmed live across 13 sizes from 1x1 to 8000x6000). A first implementation attempt trusted the docs-derived tiled formula and was wrong; caught only by a second live measurement against this project's own real fixture images before it shipped. Always confirm against the SPECIFIC real endpoint being called, even when a docs page appears to be about the right model family.

### 2026-08-02 [claude-code] — `request.is_disconnected()` does not reliably detect a real client disconnect in this deployment — use an actively-awaited `request.receive()` instead
**Context:** FEAT-016 follow-up (`POST /query/stream` heartbeat + disconnect handling). Before writing any fix, investigated live whether the app currently does anything when a client disconnects mid-stream — it didn't, confirmed with a real uvicorn server + a real httpx connection genuinely closed mid-request (not TestClient — its in-process ASGI transport was separately confirmed NOT to produce a real disconnect signal at all, so it's unusable for this class of test). The first fix attempt used `request.is_disconnected()` (FastAPI/Starlette's own documented API for exactly this) — it did NOT work: even 3+ real seconds after the client's socket was confirmably closed (`response.is_closed=True` client-side, no connection pooling), `is_disconnected()` kept returning `False` on the server. Root cause, found by reading Starlette's own source, not guessed: `is_disconnected()` wraps its `receive()` call in an immediately-cancelled `anyio.CancelScope` — a non-blocking "peek." uvicorn's ASGI receive channel only ever delivers a real `http.disconnect` message to a `receive()` call that's genuinely, continuously PENDING when the transport's own `connection_lost` fires; a call that cancels itself before that can happen never receives it, no matter how many times or how long you keep calling it.
**The actual, verified-working mechanism:** a `receive()` call that's allowed to genuinely stay pending — raced against real work via `asyncio.wait({work_task, receive_task}, ...)`, one long-lived background task per request rather than a per-check call — detected the identical real disconnect in ~20ms in the same live test. This is what `routes/query.py`'s `_watch_for_disconnect` uses; `is_disconnected()` is not used anywhere in this codebase because of this finding.
**Why this generalizes:** any FastAPI/Starlette code that needs to detect a client disconnect mid-request (long-running streaming responses, background work that should abort if nobody's listening) should NOT reach for `request.is_disconnected()` as the mechanism, despite it being the officially documented API for this — verify it actually works in your real deployment (uvicorn version, worker/loop config, and reverse-proxy-or-not can all plausibly affect this) before relying on it, the same "verify empirically, don't trust the docs/API surface alone" discipline as the entry above. The working pattern is a single background task doing a real, continuously-pending `await request.receive()` in a loop, exposing disconnected-or-not via a plain `asyncio.Event` the rest of the request can check synchronously.

### 2026-08-05 [claude-code] — Email-change confirmation completes on a bare, unauthenticated GET regardless of PKCE vs implicit flow — real gap, but SUPERSEDES an earlier same-day overstatement of it as a session-hijack primitive
**Context:** `lib/supabase/profile.ts`'s `requestEmailChange` (Settings batch 1) already found and documented that `double_confirm_changes = true` does not mean "both addresses must confirm" — confirming via EITHER the old or new address's link alone completes the email swap. A same-day independent audit (`.agent/reviews/2026-08-05-settings-audit.md`, item 2) reproduced this and then escalated it further: using a Python `supabase-py` client (which defaults to `flow_type="implicit"`, unlike this app's real client) to re-test, the audit found the bare GET also returned live `access_token`/`refresh_token` values directly in the redirect, and reported this as a full account-takeover-via-single-click primitive.
**That escalation was wrong, and the error is worth recording precisely: the test client used did not match the real app.** `@supabase/ssr`'s `createBrowserClient` (this app's actual client, confirmed in `node_modules/@supabase/ssr/dist/main/createBrowserClient.js`) defaults to `flowType: "pkce"`, not implicit. Retested with a real `@supabase/supabase-js` client configured identically to the app's (`flowType: "pkce"`): the email link's token is prefixed `pkce_`, the GET redirects to a real `?code=` query param (not a token-bearing fragment), and exchanging that code via `POST /auth/v1/token?grant_type=pkce` genuinely requires the matching `code_verifier` — confirmed at the raw-HTTP level, bypassing the SDK's own client-side guard entirely: a guessed/wrong verifier gets `400 bad_code_verifier`; an omitted one gets `400 validation_failed`; only the verifier that never left the initiating browser's own storage succeeds. **The session/token-hijack-via-bare-link claim does not apply to this app as actually configured.**
**What DOES still hold, confirmed by isolating to a single bare GET with zero exchange ever attempted:** the email address itself swaps unconditionally at GoTrue's `/auth/v1/verify?type=email_change` GET step, independent of and before any PKCE code exchange — confirmed symmetrically for both the old-address and new-address links. This is fundamental GoTrue server behavior for this verification type, not a misconfiguration: no `secure_email_change`-equivalent config flag exists (only `secure_password_change`, for passwords, itself `false` here), and this project's Supabase CLI version exposes exactly two Auth Hook points (`before_user_created`, `custom_access_token`) — no hook exists at email-change-confirmation time to intercept and add a session-binding check. Deliberate cross-device design, shared with signup/recovery/magic-link (all confirmable from a different device than the one that started the request), not something a client-side flag can override.
**Corrected severity:** not an instant one-click full account takeover. It IS a real gap: anyone with read access to *either* mailbox — not both — can force a permanent, unauthenticated email change, which is a real, if narrower, security-relevant capability (sets up a follow-on password-reset-based takeover, and defeats `double_confirm_changes`'s implied "both must agree" guarantee).
**Mitigation shipped (2026-08-05):** `requestEmailChange` now requires the account's current password (verified via a real `signInWithPassword` call, not a client-side-only check) before a change can even be INITIATED — `email-section.tsx` gates the submit button on it. This does not and cannot close the confirmation-side gap described above (raising the bar on who can START a change doesn't constrain who can CONFIRM one) — chosen deliberately over building a fully custom in-app OTP flow (which WOULD close it, by never exposing GoTrue's native link at all) after presenting both options; the residual gap is tracked in `.agent/GAPS.md`, not silently accepted.
**Why this generalizes:** (1) a test client's own defaults (flow type, storage, whatever) can silently diverge from the real application's configuration in ways that flip a finding's severity — always confirm the test harness matches the real client's actual config before trusting a security finding built on it, the same discipline the disconnect-detection entry above already established for a different layer. (2) When a fix is only partial (raises a bar rather than closing a gap), say so explicitly in both the code comment and the tracking doc — a mitigation that looks complete but isn't is worse than an honestly-labeled partial one.

### 2026-08-07 [claude-code] — Working-tree-based verification (`tsc`/`pytest`/`next dev`/e2e against local files) cannot detect "committed code depends on a file that was never committed" — STANDING GAP in this project's own verification habit, not a one-off miss
**Context:** A docs-reconciliation pass (FEATURES.md backfill) surfaced that `preferences-section.tsx` (committed 2026-08-06, `fbc4a5b`) imports `@/hooks/use-preferences`, which had never been committed at all (`git log --all` on it: empty). A user-directed fresh-clone check (real `git clone` + `pnpm install`/`uv sync` + `next build`/`pytest`, no working-tree state carried over) found **four** independent instances of this exact shape across the four most recent settings/account-deletion commits — a missing React hook, a missing SQL migration, a missing exported function (`deleteAccount`), and a missing pair of test-helper exports (`getAccessToken`/`LOCAL_SUPABASE_ANON_KEY`) — plus a fifth, adjacent bug: 6 files (3 pre-dating this session) failing `next build`'s ESLint gate (`react/no-unescaped-entities`) that `tsc --noEmit`/`next dev` never enforce. **`next build` had apparently never been run against this repo before, ever, by any session** — every verification pass in this project's history used `tsc --noEmit` (type-only, no lint) and/or `next dev` (lint warnings don't block the dev server) against the live working tree.
**Investigated, not assumed: was a fresh-clone check ever run for this class of work and did it pass wrongly, or was it skipped?** Searched the full project history (`CHANGELOG.md`, `FEATURES.md`) for every prior "fresh clone" mention — exactly one precedent exists, 2026-07-27 (FEAT-006/009's `Embedder` lazy-construction fix), and its own stated purpose was narrow: confirming the fix degrades gracefully with **no `.env` present** (i.e., a real lazy-vs-eager-credential-crash check), not "are all the files this code touches actually staged in git." **Answer: genuinely skipped, not run-and-passed** — this class of check was never adopted as a general pre-merge gate for feature work in general, only reached for specifically when a feature concerned credential/construction-timing behavior. Settings batches 1-3 and the chat-modernization batches never touched that kind of code, so nobody had a standing reason to reach for it.
**Why this generalizes, and is a standing gap not a one-off:** `tsc --noEmit`, `pytest`, `next dev`, and even Playwright e2e tests driven against a locally-running dev server are ALL structurally blind to the tracked/untracked distinction — they only see what's physically on disk in the working tree, which during active development always includes both committed AND staged-but-uncommitted AND fully-untracked files simultaneously. A component and the hook it imports can sit side-by-side on disk, one committed and one not, and every one of those checks passes identically either way. Only a real `git clone` into a separate directory (or equivalently, `git stash` + verify) removes that blind spot. **This is not specific to credential-handling code** — any multi-file feature (a component + its hook, a route + its migration, a test + its shared helper) is equally exposed, and the more files a feature touches, the more likely one lands uncommitted while its dependents don't.
**Fix pattern going forward:** a genuine `git clone` (or `git stash`) + fresh install + full build/test — not just `tsc`/`pytest` against the working tree — should be the actual gate before considering ANY multi-file feature done, not reserved for credential/construction-timing work specifically. `next build` (not just `next dev`/`tsc --noEmit`) is the only thing in this stack that has ever caught the ESLint-blocking-production-build class of issue — routine verification should include it, at least before a batch of related commits is considered closed out, not just before a deploy.

### 2026-08-18 [claude-code] — `git commit` is not `git push`, and Render reporting a deploy "live" is not proof the right code is running — SAME root category as the 2026-08-07 entry above, a different layer
**Context:** A real production incident (a 108-chunk document exhausting Voyage's 3 RPM ceiling, falling back to Gemini, then Gemini also hitting a real 429) was root-caused and fixed: neither provider's client honored its own server-supplied retry delay despite both exposing it. The fix (bounded Gemini retry parsing the real `retryDelay`; Voyage's dead `retry_after` property wired into its actual tenacity wait strategy; the tokenizer bundled into the Docker image) was implemented, tested against the exact verbatim incident payload, and committed. A second document then failed with the *identical* "both providers exhausted" error, appearing to happen after the fix was live.
**It wasn't live. The commit was never pushed.** `git log` showed the fix commit sitting on top of local `master`; `git fetch origin master` showed `origin/master` — and therefore Render's most recent live deploy — was still on the PRECEDING commit, which predates the retry fix entirely. Confirmed beyond just the SHA mismatch: real log evidence showed only 2.489s elapsed between the Voyage failure and the final Gemini `EmbedError`, structurally too short to contain even one retry honoring the real `retryDelay: 5.395s` this incident's own error payload carried, and the retry code's own unconditional per-attempt warning log line ("Gemini embed_content rate-limited (attempt %d/%d...)") never appeared anywhere in the logs — the running container was demonstrably still executing the old code, not a deploy-timing edge case.
**After pushing (and confirming Render's now-fixed auto-deploy genuinely picked it up), the next instinct was right but ran into a real platform wall:** before spending a real re-test upload, directly confirm the live container's actual source matches the pushed commit — not just trust "Render says live" a second time, having just been burned trusting it isn't even the right question (the deploy status genuinely doesn't distinguish "live because this commit built and started" from "live because some OTHER commit is still running and nothing new was ever pushed at all"). Two direct-inspection paths were tried and both are genuinely unavailable on this project's plan: SSH/exec (no `/v1/ssh-keys` management endpoint on Render's REST API — registering a key requires dashboard access this environment doesn't have) and Render's "Jobs" feature (`POST /v1/services/{id}/jobs` exists and is reachable, but rejects outright with `"new paid services not allowed"` — Jobs is a paid-tier-only feature, this service is on the free tier).
**Closed permanently, not worked around once:** `GET /health` now returns a `commit` field sourced from Render's own auto-injected `RENDER_GIT_COMMIT` env var (confirmed against Render's real docs — available at both build time and runtime for every deploy, no Dockerfile change needed; `"unknown"` outside Render). A single `curl` now answers "is the code I think is deployed actually what's running" directly, permanently, without SSH or a paid plan.
**Why this generalizes the same way the 2026-08-07 entry does:** that entry found working-tree checks can't distinguish "file exists on disk" from "file is in git" — a proxy signal mistaken for the real one. This is the identical failure shape one layer further along the pipeline: "I ran `git commit`" is not "I ran `git push`," and "the platform's dashboard/API says live" is not "the code I'm thinking of is what's executing." Every step in code-reaches-production (committed → pushed → built → deployed → actually running) has its own proxy signals that can each individually look fine while an earlier step silently didn't happen — checking the outcome directly (here: `/health`'s real `commit` field) beats trusting any single intermediate status report.

### 2026-10-06 [claude-code] — `async def` route handlers calling synchronous clients froze the whole server
**Context:** Every route was `async def` while calling the synchronous Supabase client, and `POST /query` also called the synchronous retriever, Gemini, and verifier. An `async def` handler runs on the event loop, so one `/query` (5–10s) stalled every other request on the single worker, including `/health` and other users' SSE streams and their keepalives. Measured: `/health` waited 1.76s behind a 2s blocking `/query`.
**Rule:** Handlers that touch blocking clients are plain `def`. An `async def` route must route each blocking call through `asyncio.to_thread`. `tests/test_event_loop.py` fails if a new route breaks this.

### 2026-10-06 [claude-code] — Filtering after an HNSW index scan silently starves results; reproduce it with realistic vectors
**Context:** `match_chunks_by_vector` filters by `user_id`/`document_ids`/provider, but pgvector's HNSW scan first returns the ~`ef_search` (40) nearest chunks across ALL tenants. With 400 of user B's chunks near the query, user A got 0 of their 5 chunks. Fixed with `hnsw.iterative_scan = strict_order` on the function (migration `20261006_002`).
**Gotchas found while testing:** (1) the function-level `SET hnsw.*` is rejected ("permission denied to set parameter") unless pgvector's library is already loaded in the session — the migration touches `'[1]'::vector` first. (2) Synthetic test vectors that are identical, or orthogonal to everything else, degenerate the HNSW graph (nodes become unreachable), so even iterative scan returns nothing — use varied, realistic vectors (random noise around a direction) or the test proves nothing. (3) Dead index entries left by other tests (deleted rows, not yet vacuumed) made the same scenario pass or fail depending on test order; the regression test VACUUMs first and asserts a control query (iterative scan off) really is crowded out.

### 2026-07-31 [claude-code] — Voyage embedding fallback: Gemini `gemini-embedding-2`, tracked PER CHUNK not per document
**Alternatives considered:** No fallback (accept document-level failures under Voyage's real 3 RPM ceiling); Cohere Embed v4 (native 1024-dim output, no truncation needed, but a brand-new credential/dependency); Jina Embeddings v4 (research-only license, explicitly not for production throughput per Jina's own docs); per-DOCUMENT fallback tracking (simpler, but re-embeds an entire document from scratch on any partial failure).
**Chosen:** Gemini `gemini-embedding-2` (NOT `gemini-embedding-001` — live-verified text-only, see `.agent/api-docs/gemini.md`), reached over the same `GEMINI_API_KEY`/`genai.Client(api_key=...)` path `services/parser.py`'s OCR tier already uses — no new credential. Tracking is per-chunk (`chunks.embedding_provider`), agreeing with the task brief's own reasoning: the real failure mode is a mid-batch Voyage RPM exhaustion, not a clean whole-document failure, so only the actually-failed batch's chunks should fall back — re-embedding an entire document via a different provider just because one batch hit a transient rate limit would be real wasted cost and, worse, would make an otherwise-healthy document's retrieval quality depend on an unrelated provider for no reason.
**Reasoning for provider choice:** live-verified (Step 0 of the implementing task, not trusted from research alone) that `gemini-embedding-2` accepts genuine multimodal (text+image) `Content` over the plain API-key auth path — NOT Vertex AI/service-account auth, which is what multimodal embeddings have historically required from Google. Also live-verified that `gemini-embedding-2`'s `output_dimensionality=1024` Matryoshka truncation returns an already-unit-normalized vector (norm ~1.0), unlike `gemini-embedding-001` (~0.61) — doesn't matter for pgvector's own magnitude-invariant `<=>` operator, but removes a dependency on that invariance holding everywhere. See the standing anti-pattern entry above (§Anti-patterns, 2026-07-31) before touching any code that compares vectors across `embedding_provider` values.
**Fallback trigger scope, deliberately narrow:** only `RateLimitError`/`ServiceUnavailableError`/`Timeout` (i.e. Voyage's own SDK-internal retries genuinely exhausted) fall back to Gemini. `AuthenticationError`/`InvalidRequestError` (config errors) do NOT fall back — falling back on those would silently mask a broken Voyage integration behind Gemini indefinitely instead of surfacing the misconfiguration loudly.
