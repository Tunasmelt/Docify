## 2026-07-24 — fix: FEAT-010 self-audit — delimiter-general citation parsing, sign handling, figure-image validation
**Phase:** 2 (Retrieval + Generation)
**Feature:** FEAT-010
**Decision:** A self-audit of FEAT-010's most significant finding (the live-discovered grouped-bracket citation bug) checked whether that fix generalized or was narrower than it looked, plus independently re-verified four other design claims. Found and fixed three real gaps; two claims held up unchanged.

**Citation parsing was still delimiter-specific — found via synthetic variants beyond the one real captured case:** the shipped fix matched `\[(\d+(?:\s*,\s*\d+)*)\]` — comma-separated digits only. A semicolon variant, `[2; 3]`, reproduced the identical silent-drop failure under a different delimiter (matched nothing at all, no signal). `[2,3]` (no space), `[2 , 3]`, `[10, 2]` (multi-digit), and `[2][3]` (separate brackets) all already worked. Rather than special-case delimiters one at a time, redesigned to match any non-nested bracket span (`\[([^\[\]]*)\]`) and pull every integer out of its contents regardless of separator — the actual invariant is "citations are digit runs inside a bracket," not "citations are comma-separated." Nested/malformed brackets (`[2, [3]]`) remain a deliberate, documented gap (the outer number is dropped, the inner `[3]` still parses) — judged reasonably out-of-scope since Gemini has never been observed producing this shape, unlike the semicolon case which was a direct structural analog of an already-confirmed real bug.

**`[-1]` and `[0]` were failing differently, not the same safe way:** `[0]` was correctly flagged hallucinated (0 is outside the 1-indexed range), but `[-1]`'s digit-only extraction (`\d+`) silently stripped the minus sign and treated it as a **valid** citation to chunk 1 — a structurally-possible model output silently miscited rather than rejected. Fixed by capturing an optional leading `-` (`-?\d+`) so `int("-1") == -1` fails the same range check `0` already fails. Brackets with no digits at all (`[citation needed]`, a literal `[N]` placeholder, empty `[]`) are confirmed to correctly produce neither a cited nor a hallucinated entry — not citation-shaped, correctly ignored rather than flagged as noise.

**`GeneratorChunk` had no protection against a figure missing its image:** confirmed live — constructing `GeneratorChunk(element_type="figure", image=None)` succeeded silently, and `_build_contents()` sent it to Gemini as a text-only chunk with zero signal an image was expected. Since `parser.py` already drops any figure element whose image extraction failed (it never becomes a chunk at all — see FEAT-004), a figure-typed `GeneratorChunk` reaching `Generator` with no image can only mean a future FEAT-012 implementation failed its own Storage fetch step, never a legitimate state. Added a `__post_init__` guard raising `ValueError` on construction — matches this project's established discipline of enforcing an invariant at the thing that needs it true, not trusting whoever happens to call it correctly today (`.agent/MEMORY.md`'s "no current caller violates an invariant" lesson, FEAT-007/009).

**Re-verified, unchanged:** (1) `[N]`-is-position-not-chunk_id holds structurally — grepped `generator.py` for `chunk_id`, confirmed it appears only in comments/the dataclass field, never in `SYSTEM_INSTRUCTION` or `_build_contents()`'s output; a canary chunk_id (`LEAK-CANARY-99999999-abcdef`) round-tripped through `_build_contents()` and confirmed absent from the actual text sent to Gemini. (2) Figure-only multimodal holds structurally against `parser.py`/`chunker.py` read directly (not the prior summary): all six `ElementType` values traced through both files, only the `FIGURE` branch ever assigns a real image (`content = image` in `parser.py:153`; `image = element.content` in `chunker.py:344`, with the `TABLE` branch on the same conditional explicitly setting `image = None`). `generator.py` itself has no separate `element_type == "figure"` check to drift from that truth — `_build_contents()` gates purely on `chunk.image is not None`, deferring entirely to the single upstream source of truth rather than maintaining a second, driftable copy of the same invariant.

**Reported numbers reproducible-in-character, not a fluke:** re-ran Q1 ("Angola's HDI value in 2010?") independently — fresh ingestion, fresh real Voyage/Gemini calls, same fixture. `input_tokens` matched exactly (1256 — deterministic, same retrieved context/question), `output_tokens` 31 vs the original 26, `latency_ms` 2326.4 vs 2148.3 — differs as expected for a real API call, same order of magnitude, not identical, not a one-time anomaly.

**Verification:** 4 new/expanded permanent tests in `test_generator.py` (grouped-bracket parametrized variants including the semicolon case; nested-bracket documented-gap test; negative/zero-marker-parity test; no-digit-bracket test; figure-with-no-image construction-refusal test; non-figure-with-no-image allow test) — full file: 21 passed, 2 skipped (up from 10 passed, 2 skipped before this audit).
**Changed:** `apps/api/services/generator.py` (citation regex redesigned, sign handling fixed, `GeneratorChunk.__post_init__` guard added), `apps/api/tests/test_generator.py` (10 → 21 tests).
**Impact:** The one finding this session's own summary flagged as needing independent re-verification (item 1) turned out to be real — the shipped fix was narrower than "verified against one real example" suggested. Two additional real gaps (sign handling, silent figure-image omission) were found by the same discipline applied to claims the summary hadn't flagged as risky, reinforcing that "spot-check the highest-confidence claim first" is the right default for this project's self-audits, not just the one already suspected.
**Rollback:** Revert `apps/api/services/generator.py` and `apps/api/tests/test_generator.py`.

## 2026-07-24 — feature: Gemini generator wrapper (FEAT-010)
**Phase:** 2 (Retrieval + Generation)
**Feature:** FEAT-010
**Decision:** First feature to call Gemini for generation (not just OCR fallback), and the first point where retrieval quality (FEAT-009) and generation quality compound — a correct top-5 chunk is wasted if the generated answer doesn't actually cite it. `.agent/api-docs/gemini.md` had only model IDs/pricing from the FEAT-006-era provider-swap decision, flagged then as a known gap — ran `/api-check gemini` for real before writing any code: doc had no verified date on the request/response section, so the actual `generate_content` signature, `Part.from_bytes`/`Part.from_text` construction, `system_instruction` config field, and `usage_metadata`/`model_version` response shape were all verified directly against the installed `google-genai` 1.7.0 SDK source (`models.py`, `types.py`, `client.py`), not docs prose or memory — appended to the cached doc with file:line references.

**`[N]` citation markers are positions, not chunk IDs — a deliberate, documented decision:** the model only ever sees chunks numbered `[1]..[len(chunks)]` in the prompt and has no way to know a chunk's real database id, so it structurally cannot cite one. `GenerateResult.cited_indices` returns 1-indexed positions into the `chunks` argument; FEAT-012 must map each back to `chunks[position - 1].chunk_id` itself. Written explicitly into both the system prompt (the model is told the number is a position, "NOT any database id") and FEAT-010's acceptance criteria, so this isn't left implicit for FEAT-012 to guess.

**`GeneratorChunk`, not FEAT-009's `RetrievedChunk` — a scope boundary, also documented forward:** `RetrievedChunk` carries no image data (the RPC functions it calls never `SELECT figure_path`), and `Generator` has no Storage client of its own. Rather than reach into `retriever.py` (not in this feature's file list) to plumb `figure_path` through, `Generator` defines its own input type, `GeneratorChunk` (with an `image: bytes | None` field), and FEAT-012's acceptance criteria now note it must fetch each figure chunk's image from Storage and adapt `RetrievedChunk` rows into `GeneratorChunk` before calling `generate()`.

**Multimodal:** only `element_type == "figure"` chunks ever carry image bytes (confirmed against `parser.py`: tables are exported to markdown text via Docling, never rendered as an image) — `_build_contents()` emits a text `Part` per chunk (numbered header + content) followed by an inline-bytes `Part` (`image/png`) only when present, verified via a mocked test asserting the exact bytes/mime-type reach `generate_content`'s `contents` list, and that non-figure chunks never produce an image part even when they have content.

**Hallucinated citations fail safely, not silently:** a `[N]` marker outside `1..len(chunks)` is dropped from `cited_indices`, surfaced in a new `GenerateResult.hallucinated_markers` field, and logged — never raises, never silently treated as valid. Verified via a mocked test forcing a `[7]` reference against a single-chunk context.

**A real parsing gap found live, not in review:** the compound retrieval+generation quality test (below) surfaced that real Gemini answers sometimes group multiple citations into one bracket — `[2, 3]`, `[1, 2, 4]` — despite the system prompt asking for the singular `[N]` form. The original regex (`\[(\d+)\]`) silently failed to match these, dropping every number inside a grouped bracket from both `cited_indices` and `hallucinated_markers` with no signal anything was missed — confirmed against the actual captured real answer text: pre-fix, question 4's `cited_indices` was `[2, 4, 1]`, silently missing position `3` from a `[3, 4]` bracket; post-fix, directly re-run against that same real text, `cited_indices` is `[2, 3, 4, 1]`. Fixed by matching the whole bracket (`\[(\d+(?:\s*,\s*\d+)*)\]`) and splitting on comma. Locked in as a permanent regression test using the real grouped-bracket shape observed live, not a synthetic guess at what might occur.

**Retrieval + generation compound quality, real end-to-end, item 4's explicit requirement:** reused FEAT-009's exact `table_heavy.pdf` fixture and 4 questions — real Docling parse, real Voyage embed, real `Retriever.retrieve()`, real `Generator.generate()` per question (25s Voyage-pacing preserved between questions, same real free-tier constraint as FEAT-009). **4/4 answers cited the exact chunk position retrieval had already proven relevant** — real token counts and latencies: Q1 1256in/26out/2148ms, Q2 856in/14out/2155ms, Q3 1778in/128out/4764ms, Q4 904in/347out/5885ms. A single-chunk smoke test (`RUN_REAL_GEMINI_TEST=1`) separately confirmed basic real-call correctness: 215in/19out/1969ms, correct `[1]` citation, no hallucination.

**Changed:** `apps/api/services/generator.py` (new), `apps/api/tests/test_generator.py` (new, 10 fast tests + 2 gated real/quality tests), `.agent/api-docs/gemini.md` (request/response shape section added), `.agent/FEATURES.md` (FEAT-010 → complete, with the position-vs-id and `GeneratorChunk`-vs-`RetrievedChunk` decisions written into acceptance criteria for FEAT-012 to read).
**Impact:** FEAT-012 (`/query`) now has a generation layer proven to cite correctly against real retrieval output, with both of its open forward-dependencies (citation-position mapping, figure-image plumbing) written down explicitly rather than left for FEAT-012 to rediscover — matching FEAT-009 self-audit's "no current caller violates an invariant" lesson: writing the requirement down now, before the caller exists, rather than after.
**Rollback:** Remove `apps/api/services/generator.py`, `apps/api/tests/test_generator.py`; revert `.agent/api-docs/gemini.md` and `.agent/FEATURES.md`.

## 2026-07-24 — test: FEAT-009 self-audit — RPC tenant scoping, DEFINER/INVOKER, concurrency failure mode, rank-2 quality margins
**Phase:** 2 (Retrieval + Generation)
**Feature:** FEAT-009
**Decision:** A 7-item self-audit of `match_chunks_by_vector`/`match_chunks_by_fts` and `Retriever`, targeting the exact class of bug this project has caught before: an invariant that's true only because of how callers happen to behave today, not because the thing that needs it true enforces it itself (FEAT-007's `storage_path` precedent). All 7 items verified live, not restated from the original implementation's own claims.

1. **WHERE-clause scoping:** both functions filter `where c.user_id = match_user_id and c.document_id = any(match_document_ids)` — read directly from the committed migration SQL. No path where `user_id` goes unused.
2. **DEFINER vs INVOKER:** live `pg_proc.prosecdef` query confirms both functions are `false` (SECURITY INVOKER, the default — not accidentally escalated). RLS bypass happens because `service_role.rolbypassrls = true` (confirmed via `pg_roles`), not function ownership — the explicit WHERE clause from item 1 is the actual, sole tenant boundary, exactly as the migration's own comments claim.
3. **`user_id` provenance:** `Retriever` has no HTTP/JWT awareness and never re-derives `user_id` — it trusts whatever its caller passes, same shape as `run_ingest_pipeline`'s already-audited `user_id` handling. Exhaustive grep (`Retriever|retriever` across `routes/` and `main.py`; `\.retrieve(` across all of `apps/api`) found **zero production callers** — every call site is `tests/test_retriever.py`. FEAT-012 (`/query`, not yet built) will be the first production caller. Not a current bug, but a real forward-looking requirement — documented directly on FEAT-012's acceptance criteria in `.agent/FEATURES.md` rather than left implicit.
4. **SQL-layer isolation, adversarial:** two real users, identical content **and identical embedding**, both RPC functions called directly (bypassing `retrieve()` entirely) with `match_document_ids` deliberately including *both* users' documents — to prove `match_user_id` alone does the isolation work, not `document_ids`. User A's call returned only chunk A, user B's only chunk B, for both functions. Isolation holds at the SQL layer independent of the Python layer.
5. **Concurrency partial-failure:** live monkeypatch of `_vector_search`/`_fts_search` (both directions) confirms a `ThreadPoolExecutor` worker exception re-raises cleanly on `.result()` — no silent partial-result path. Locked in as a permanent parametrized regression test rather than left as a one-off check.
6. **Rate-limit pacing isolation:** `test_retriever.py` run alone measures ~3.4-3.8s pytest-internal test time against the file's own real Voyage calls; the ~19s wall-clock gap is Python/Docling/torch import overhead shared by every test file, not the gated test's 25s pacing (which is inline in one `skipif`-gated function body, never executes in routine runs, and isn't a shared fixture — can't compound with FEAT-010/011's future tests).
7. **Rank-2 margins:** raw (pre-fusion) scores pulled directly from `_vector_search`/`_fts_search`, bypassing RRF, since RRF's rank-based formula produces a near-constant score gap between adjacent ranks regardless of the true underlying match quality. Vector-distance gaps for both rank-2 cases are razor-thin (~1-2%); FTS-rank gaps are substantial (~31-47%) — both signals agree, and the gap is explained by genuine content overlap in the fixture PDF (an earlier draft of the same accounts table; the Masters-only version of the same course listing), not the expected chunk being under-ranked by a bug.

Items 1-5 came back clean — nothing met the task's "stop and flag before FEAT-010" condition. Item 3's finding is real but forward-looking (captured as an acceptance-criterion note, not a code change, since there's no current caller to fix). Item 7 confirms the original quality test's rank-2 results are a reasonable near-tie, not a retrieval defect.
**Verification:** `test_a_failing_search_method_raises_rather_than_silently_returning_partial_results` (parametrized over `_vector_search`/`_fts_search`) added to `apps/api/tests/test_retriever.py` as a permanent regression test for item 5; passing (`test_retriever.py`: 10 passed, 1 skipped). All other items verified via throwaway scratch scripts (direct RPC calls, raw-score probes), deleted after use — no other file changes.
**Changed:** `apps/api/tests/test_retriever.py` (10 → 11 tests), `.agent/FEATURES.md` (FEAT-012 acceptance criteria: added `user_id` provenance requirement).
**Impact:** FEAT-009's RPC-based tenant scoping is now independently, adversarially verified at the SQL layer (not just asserted by the feature that built it), and FEAT-012 has an explicit, written requirement for the one invariant this audit found isn't yet enforced anywhere in code (because nothing calls it yet).
**Rollback:** Revert `apps/api/tests/test_retriever.py` and `.agent/FEATURES.md`.

## 2026-07-24 — feature: Retriever service, hybrid search + RRF (FEAT-009)
**Phase:** 2 (Retrieval + Generation)
**Feature:** FEAT-009
**Decision:** First Phase 2 feature, and a different verification shape from everything before it: Phase 1's features needed to prove correctness and safety (does it run, is it isolated, does it not corrupt data); this one additionally needs to prove *quality* — does hybrid search actually find the right content for a real question, which has no prior precedent in this project to lean on.

**Why a new migration, not just `retriever.py`:** neither pgvector cosine ranking (`embedding <=> query_embedding`) nor Postgres FTS ranking (`ts_rank`) is expressible through PostgREST's REST query builder — `.select()`/`.order()` only support plain column comparisons and a fixed operator set, not arbitrary SQL expressions in `ORDER BY`. The standard, documented way to do this through Supabase's REST layer is a Postgres function called via `client.rpc(...)`. Added `apps/api/migrations/20260724_001_hybrid_search_functions.sql` — `match_chunks_by_vector` and `match_chunks_by_fts`, both taking `match_user_id`/`match_document_ids` as explicit function parameters and filtering on them directly in the `WHERE` clause (per this task's explicit requirement: scoped explicitly, not relying on RLS alone — these functions are only ever called with the service-role client, which bypasses RLS entirely, so the explicit filter is the actual tenant boundary, matching FEAT-007/008's established pattern). `EXECUTE` revoked from `PUBLIC` (Postgres's default for new functions) and granted only to `service_role`. Applied and verified against the real local Supabase stack before any Python code was written — confirmed vector-distance ordering, FTS ranking, and user_id scoping all work correctly via a throwaway probe script, deleted after use.

**Why `embedder.py` also changed:** Voyage's embeddings are asymmetric — query-side and document-side calls use different internal prefixes for better retrieval quality (documented in `.agent/api-docs/voyage.md` since FEAT-006, flagged there at the time as "a separate concern... not addressed here"). `Embedder.embed()` hardcodes `input_type="document"` for ingestion; embedding a bare query string through it would silently degrade retrieval quality. Added `Embedder.embed_query(text) -> Vector`, a small, additive, `input_type="query"` counterpart — `embed()`'s own signature and behavior are unchanged, so this doesn't touch FEAT-006/007's existing tested behavior.

**RRF, and the naming confusion this task explicitly called out:** `RRF_K = 60` (the fusion constant, dampens the influence of low ranks in `1/(RRF_K + rank)`) and `DEFAULT_K = 8` (the retrieval count, per `.agent/SCOPE.md`'s Phase 2 spec) are two completely different numbers that happen to share a letter — confusing them produces a plausible-looking but wrong result with no error to catch it. Named unmistakably differently in code (not just documented as different in prose), and `test_merges_via_reciprocal_rank_fusion_k_60_default` hand-computes expected fused scores for a case designed to make the distinction concrete: vector search's own #1 pick and FTS's own #1 pick both individually lose to a chunk that ranked #2 (not #1) in *both* — the textbook demonstration of why hybrid fusion beats either single ranking, and a case sensitive enough that a swapped constant would visibly break it.

**Parallelism — the one place in this codebase with real thread-level concurrency:** vector search and FTS search are independent read-only queries with no dependency on each other's results, so `Retriever.retrieve()` runs them via a `ThreadPoolExecutor`, proven with real wall-clock timing (two 0.4s-sleeping fake search methods complete in ~0.4s total, not ~0.8s) rather than just asserting both got called. Everywhere else in this codebase is fully synchronous end to end despite `async def` route signatures (see `.agent/reviews/2026-07-23-efficiency.md`) — this is a deliberate, narrow exception because these two calls genuinely are independent, not a broader shift in the codebase's concurrency model.

**Testing shape — correctness and quality kept deliberately separate:** 8 fast/structural tests insert chunk rows directly with hand-crafted, precisely-controllable embeddings (vectors placed along orthogonal/parallel axes so relative cosine distances are exactly known, not approximated) and a fake query embedder — real local Postgres/pgvector/FTS, no real Docling/Voyage, matching FEAT-006's own testing pattern. These cover: the basic signature/return type, real concurrent execution (timing-proven), RRF math (both the disagreement case above and a chunk found by only one method), top-k truncation with full metadata round-tripping, explicit `user_id`/`document_ids` parameter passing (spied on the real `.rpc()` calls), and multi-tenant isolation (two real users, **identical content and identical embedding** in both — the strongest version of this test, since if scoping didn't work the two chunks would tie or beat each other, not just both show up — plus a positive control proving the absence is real scoping and not a broken query returning nothing for anyone).

**Retrieval quality — real results, not just pass/fail, per this task's explicit requirement:** `table_heavy.pdf` ingested through the real `Parser`/`Chunker`/`Embedder` (real Docling parse, real Voyage embeddings — no fakes for this one test), 4 questions built from content read directly out of that real ingestion's actual chunk text this session (not recalled from an earlier session's report):

| Question | Expected content | Result (of 5 returned) |
|---|---|---|
| What is Angola's Human Development Index value in 2010? | Table 19 (HDI), Angola row | **rank 1** |
| Does Respondent C have a driving licence? | Table 14, "Do you have a driving licence?" row | **rank 1** |
| What was the balance in the 2011 accounts? | Table 18 (accounts, 2011), "Balance" row | **rank 2** — Table 17 (an earlier draft of the same accounts table, same figures) ranked 1st |
| What courses does Institution X offer in Mathematics? | Table 15 (courses, Institution X), Mathematics row | **rank 2** — Table 16 ("Masters courses offered by Institution X", same institution) ranked 1st |

4/4 found their expected chunk in the top-5; the two rank-2 results were both edged out by a genuinely closely-related table from the same document (an earlier draft of the same accounts table; the Masters-only version of the same course listing), not an irrelevant result — a reasonable outcome, not a quality miss. Full ranked output (all 5 results per question, with scores and content previews) printed by the test itself.

**A real infrastructure constraint hit and handled honestly, not silently worked around:** the quality test's first run hit a genuine Voyage `RateLimitError` on its 3rd query-embed call — this Voyage account has no payment method on file, capping it at 3 RPM, and the test's ingestion-embed call plus first two query-embeds had already used part of that budget within the same rolling window even at 21s spacing. Fixed by pacing every real Voyage call in the test 25s apart (including a pause after ingestion, before the first query), with an inline comment explaining this is a real account-level constraint, not a bug in `Retriever` or `Embedder` being papered over. Re-ran clean after the fix.

**Changed:** `apps/api/services/retriever.py` (new), `apps/api/services/embedder.py` (`embed_query()` added, `embed()` unchanged), `apps/api/migrations/20260724_001_hybrid_search_functions.sql` (new), `apps/api/tests/test_retriever.py` (new, 10 tests), `.agent/FEATURES.md` (FEAT-009 → complete).
**Impact:** FEAT-012 (the actual product Q&A loop) can now build against a retriever whose relevance has been empirically demonstrated on real content, not just assumed from passing unit tests — the thing this task called out as having no prior precedent in this project and being the part FEAT-012 will actually depend on. Full backend suite: **130 passed, 3 skipped** (the three intentionally-gated real-API/e2e/quality tests) — no regressions.
**Rollback:** Remove `apps/api/services/retriever.py`, `apps/api/tests/test_retriever.py`; revert `apps/api/services/embedder.py` and `.agent/FEATURES.md`; drop the two functions in `apps/api/migrations/20260724_001_hybrid_search_functions.sql` (rollback SQL included in that file).

## 2026-07-23 — fix: delete_document Storage failures now return a proper error envelope (FEAT-008 self-verification follow-up)
**Phase:** 1 (Ingestion Pipeline)
**Feature:** FEAT-008
**Decision:** A self-verification pass on FEAT-008's own claims (run live, not re-asserted) found one real gap: `delete_document`'s two Storage `.remove()` calls (uploads bucket, figures bucket) had no error handling. A simulated partial failure — figures removal throwing while uploads removal succeeds — confirmed the underlying retry-safety was already correct (document row and chunks survive intact, a retry succeeds cleanly, `.remove()` on an already-gone object doesn't itself error), but the *first* failure surfaced as a bare, unhandled 500 with no error envelope and no server-side log line — indistinguishable from a genuine bug if it ever happened in practice. Fixed by wrapping each `.remove()` call individually (so the failing bucket — uploads vs figures — can be identified precisely) and returning the standard error envelope with a new `STORAGE_ERROR` code (500 — a transient infrastructure failure, not a client error) whose message tells the caller the document was not modified and retrying is safe. The corresponding ERROR log line records only `document_id`/`user_id`/which bucket failed — never the exception's own message or a traceback, since a Storage error's message isn't guaranteed not to embed the object path itself (identical discipline to FEAT-007's `StoragePathError` logging fix: coarse reason over raw detail).
**Verification:** two new regression tests turn the original live one-off check into a permanent one. `test_delete_returns_storage_error_envelope_when_figures_removal_fails` reproduces the exact scenario found live (figures `.remove()` raises, uploads succeeds) via a client wrapper that proxies every real call through to the real local Supabase client except one bucket's `remove()` — confirms the response is now `500`/`STORAGE_ERROR` (not a bare 500), confirms the log line contains `document_id`/`user_id`/`bucket=figures` and does *not* contain the raw simulated exception text, and confirms the document row and both chunks survive untouched. `test_delete_retry_after_partial_storage_failure_succeeds` continues from the same failure and issues a second, unpatched DELETE — confirms `204`, confirms the already-gone uploads object doesn't cause a second failure, confirms the document/chunks/figures object are all fully gone afterward. Manually re-ran the first test with `-s --log-cli-level=ERROR` and read the actual line: `delete_document: Storage removal failed for document <uuid> (user <uuid>), bucket=figures` — confirmed by eye, matching the established pattern from FEAT-007's own log-leak fix.
**Corrected:** `API_CONTRACT.md`'s error-code table gets a new `STORAGE_ERROR` (500) entry.
**Changed:** `apps/api/routes/documents.py` (`_storage_deletion_failed` helper, both `.remove()` calls wrapped), `apps/api/tests/test_documents.py` (6 → 8 tests), `.agent/API_CONTRACT.md` (new `STORAGE_ERROR` code).
**Impact:** A real Supabase Storage outage during `DELETE /documents/{id}` now produces a clear, actionable error response and a diagnosable log line instead of looking like an unexplained server crash — closes the one real gap found during FEAT-008's self-verification pass. Full backend suite: **122 passed, 2 skipped** (the two intentionally-gated real-API/e2e tests) — no regressions.

## 2026-07-23 — feature: `/documents` list + detail + delete (FEAT-008)
**Phase:** 1 (Ingestion Pipeline)
**Feature:** FEAT-008
**Decision:** Implemented `GET /documents`, `GET /documents/{id}`, `DELETE /documents/{id}` per API_CONTRACT.md. Ownership checks use the same pattern established in FEAT-007: the service-role client with an explicit `.eq("user_id", user_id)` baked into the query itself, not a separate ownership check after fetching by id — `db/queries.get_document()` scopes both `id` and `user_id` in one query, so "doesn't exist" and "belongs to another user" produce the identical empty result and therefore the identical 404, with nothing to accidentally leak (per this task's explicit requirement, same discipline as FEAT-007's `storage_path` hardening). Pagination is keyset-based on `created_at desc` (the existing `documents_user_idx` already indexes exactly this), fetching `limit + 1` rows to detect a next page without a separate count query; the opaque cursor is `base64(created_at)` — a documented simplification, not a full `(created_at, id)` compound tiebreak, since two documents sharing a byte-identical timestamp isn't a realistic scenario given each document is created via a separate sequential API call. An invalid `?status=` value is validated against the schema's real enum before it reaches PostgREST, rather than surfacing a raw "invalid input value for enum document_status" Postgres error as a 500.
**DELETE cascade, three distinct mechanisms, not one:** `chunks` and `citations` cascade automatically at the DB level (`on delete cascade` FKs, already in the schema — nothing new needed). `conversations.document_ids` is a plain array column, not a foreign key, so Postgres never cleans it on its own despite the contract explicitly requiring "all references from conversations" — `remove_document_from_conversations()` finds every conversation whose array contains the document (via Postgres's array-contains operator) and rewrites the array without it. Storage objects (the uploaded PDF, any figure PNGs) are removed via explicit Storage API calls. Figure paths are read from `chunks` before the DB delete, since the delete cascades those rows away.

## 2026-07-23 — fix: **SECURITY** — path traversal in `/ingest`'s storage_path allowed reading another tenant's file (FEAT-007)
**Phase:** 1 (Ingestion Pipeline)
**Feature:** FEAT-007
**Severity:** High — confirmed exploitable, not theoretical. Any authenticated user could get the ingest pipeline to download, parse, chunk, and embed another user's document into their own `chunks` (a real cross-tenant content leak), by supplying a crafted `storage_path` in an otherwise-normal `POST /ingest` request. No special access or timing was required — one JSON body field.
**Decision:** Found via a proactive self-audit (run ahead of a separate, parallel Codex security/perf review specifically because it was cheap to check and would have been flagged either way — not deferred, fixed immediately ahead of everything else per explicit instruction, blocking FEAT-008 and the broader review). The root cause: `storage_path` ownership was checked with `storage_path.startswith(f"uploads/{user_id}/")` — a literal string comparison with no understanding of `".."` path semantics. `"uploads/{attacker}/../{victim}/file.pdf"` satisfies that check (it genuinely starts with the attacker's own prefix as a string) while Supabase Storage's own server resolves the `".."` when actually fetching the object — confirmed two independent ways against the real local Storage stack: via the `storage3` SDK (the exact call `run_ingest_pipeline()` makes) and via a raw HTTP request straight to the Storage REST API, bypassing our SDK entirely. Both returned the victim's real file content. Because `run_ingest_pipeline()` downloads using the **service-role client**, which bypasses RLS entirely, the string check was the *only* authorization gate standing between an attacker-controlled path and a fully-privileged file read.
**First fix attempt was ALSO proven exploitable — this matters, don't skip it:** the initially "obviously correct" fix (reject any raw `".."` path segment, require `posixpath.normpath(path) == path`) was tested live before being trusted, and failed: a percent-encoded variant, `"uploads/{attacker}/%2e%2e%2f{victim}/file.pdf"`, contains no literal `".."` and is already normpath-canonical, yet still resolved to the victim's file — some layer in the request chain decodes `%2e%2e` back to `..` before our check ever sees it (standard, spec-compliant behavior per RFC 3986, not a bug in Supabase). Enumerating every spelling of `".."` is a losing game, so the final fix does not attempt it: `validate_storage_path()` (new, in `apps/api/routes/ingest.py`) checks the trusted `"uploads/{user_id}/"` prefix (built server-side from the verified JWT, never from client input), then requires everything after it to match a narrow character whitelist (`^[A-Za-z0-9._-]+$`) with **no path-separator character — literal or encoded — possible by construction**. This closes the entire bypass class (known variants and not-yet-invented ones) rather than pattern-matching against known-dangerous spellings. The literal-`".."` and normpath-equality checks from the first attempt are kept as a cheap extra layer, not as the primary defense.
**Single shared function, both call sites:** `validate_storage_path()` is called from both `post_ingest()` (the synchronous 403 path, before any document row is created) and `run_ingest_pipeline()` itself (the defense-in-depth check added in FEAT-007's prior Codex-review follow-up) — one implementation, not two that could drift, per this task's explicit requirement.
**Verification — proven at four levels, not just unit tests:** (1) a fast unit-level matrix directly against `validate_storage_path()` — literal traversal, percent-encoded traversal, mixed literal+encoded, absolute path, non-canonical double-slash, and a normal valid path (must still pass) — 8 cases, all correct; (2) route-level tests (`test_ingest_route_rejects_path_traversal_storage_path`, parametrized over all three traversal spellings) confirming `403` and zero document rows created; (3) pipeline-level tests calling `run_ingest_pipeline()` directly, bypassing the route, confirming `status='failed'` and zero chunk rows; (4) **the literal live proof-of-concept re-run in reverse**, per this task's explicit instruction not to trust the unit tests alone — a real user A uploads a real file with real, identifiable secret content, a real unrelated user B attempts the exact two exploit strings that previously succeeded against the live stack, both now blocked with `403` before any Storage call is made, and a standalone confirmation script (mirroring the original recon probe exactly) shows `validate_storage_path()` raising before `client.storage.download()` is ever reached for either variant. `tests/test_ingest.py` grew from 10 to 23 tests. Full backend suite re-run after the fix: **112 passed, 2 skipped** (the two intentionally-gated real-API/e2e tests) — no regressions.
**Changed:** `apps/api/routes/ingest.py` (`validate_storage_path()`, `StoragePathError`, `_SAFE_FILENAME`; replaces the old `_storage_path_belongs_to_user`/`IngestInvariantError`; both `post_ingest()` and `run_ingest_pipeline()` now call the one shared function), `apps/api/tests/test_ingest.py` (10 → 23 tests), `.agent/MEMORY.md` (new `§Anti-patterns` entry: `startswith()` is not a safe authorization boundary for path-like input — distinct lesson from the two "invariant not enforced" findings already logged, since the failure mode here is a different kind: the check ran in the right place every time and was still wrong).
**Impact:** The confirmed cross-tenant file-read via `/ingest` is closed. `run_ingest_pipeline()`'s only remaining trust in `storage_path` is that it's a `{uuid}.{ext}`-shaped string directly under the caller's own trusted prefix — nothing else about its content can route the pipeline anywhere else, encoded or not. This was fixed ahead of FEAT-008 and the parallel Codex review, per explicit instruction that this class of finding blocks everything else until closed, tested, and the live proof-of-concept confirmed dead — not batched with other findings for a single triage pass.
**Rollback:** Revert `apps/api/routes/ingest.py` and `apps/api/tests/test_ingest.py` to their pre-fix state; revert `.agent/MEMORY.md`. Not recommended — this would reopen a confirmed, live cross-tenant vulnerability.

## 2026-07-23 — feature: `/ingest` endpoint, full pipeline wiring (FEAT-007)
**Phase:** 1 (Ingestion Pipeline)
**Feature:** FEAT-007
**Decision:** This is the first place FEAT-001/003/004/005/006 meet in one real path — a document uploaded to Storage, authenticated, parsed, chunked, embedded, and persisted, scoped by a real user. `POST /ingest` validates `storage_path` starts with `uploads/{jwt.user_id}/` before anything else (403 otherwise, matching API_CONTRACT.md's stated ordering), rejects non-PDF `mime_type` (422 — Phase 1 is PDF-only per SCOPE.md), creates a `documents` row (`status='uploaded'` by DB default), and schedules `run_ingest_pipeline` as a FastAPI `BackgroundTask` before returning `202`. That function is the real pipeline: download from Storage → `Parser.parse()` → `Chunker.chunk()` → `Embedder.embed()` → upload figure `PIL.Image`s to the `figures` bucket → one bulk INSERT of every chunk row → `status='ready'`. Every stage dependency (`client`, `parser`, `chunker`, `embedder`) is injectable via keyword args defaulting to the real production objects — the route exposes this through a `get_pipeline_runner` FastAPI `Depends` hook so tests override it with `functools.partial(run_ingest_pipeline, parser=Fake..., ...)`, real constructor injection into the real function rather than `unittest.mock.patch`, matching STANDARDS.md's stated preference. `documents.status` only models coarse phases (`uploaded`/`parsing`/`embedded`/`ready`/`failed` — SCHEMA.md's enum has no "chunked" value), so `parsed_at`/`page_count` are stamped as milestones inside the `parsing` phase rather than driving their own status value — a judgment call made explicit here since the spec didn't pin it down. `page_count` is an honest approximation (max page number among *extracted* elements, not a Docling-native page count) — documented as such rather than silently presented as exact. `db/queries.py`'s `build_chunk_rows` bridges chunker.py's richer `Chunk` objects (which can span multiple pages/source elements) onto the schema's flat per-row `page_number`/`bbox` columns: `page_number` takes the earliest page a chunk touches, `bbox` comes from the chunk's first source element (always the table/figure itself for TABLE/FIGURE chunks), and nothing is actually lost — the full page list, source element indices, and caption-association provenance all go into `metadata`.
**No-partial-chunk-data guarantee (SCOPE.md):** architectural, not just tested-around.
