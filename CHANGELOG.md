## 2026-07-23 — fix: chunker size ceiling + Tier-2 test coverage (FEAT-005 Codex follow-up)
**Phase:** 1 (Ingestion Pipeline)
**Feature:** FEAT-005
**Decision:** A Codex review of `chunker.py` found one architecturally real gap (nothing capped chunk size before it reached FEAT-006's embedding calls — a large enough table or paragraph could reach Voyage's real limits with no signal) and one test-coverage gap (Tier-2 tie-breaking was correct per Codex's own manual probing but none of it was a permanent test). No cached `.agent/api-docs/voyage.md` existed yet, so per the project's own `/api-check` rule, verified Voyage's real limits live before writing any ceiling logic rather than guessing: **32,000 tokens per input, 320,000 per batch of ≤1,000 inputs** (confirmed via two independent lookups, consistent). Added `MAX_CHUNK_TOKENS = 4000` — about 1/8 of the real limit, deliberately not hugging it. Oversized `TABLE` chunks split by row group: the markdown header + separator row are repeated on every part (so each split is a self-contained, valid table on its own), body rows are grouped up to the ceiling, and a single row that alone exceeds it is kept whole rather than broken. Oversized `TEXT`/`HEADING` content splits at paragraph boundaries first, falling back to sentence boundaries only for a paragraph that's still oversized alone — never mid-sentence, matching the same "keep something oversized whole over violating the boundary rule" philosophy as the row-splitting case. Splitting happens as a post-processing pass *after* caption association and chunk-building complete, not folded into that logic — every split part inherits its parent chunk's `association_method` and `merged_caption_ids` verbatim and gains a new `split_from_element_id` (the original element's `element_id`) so a reader can tell several `chunk_index` values were originally one element. `chunk_index` assignment moved to a final pass over the fully-expanded (post-split) chunk list, since splitting can now change the total chunk count. Converted Codex's manual synthetic probes into 6 permanent regression tests: equidistant reading-order candidates broken by bbox distance, reading-order-distance beating a physically-closer-but-farther-in-reading-order candidate, two captions competing for one target (first-in-document-order wins, confirmed via `claimed_targets`), a fully-equal tie falling back to `elements` list order (Python `min()` stability), plus 2 tests for the new splitting behavior and 2 for reparse stability (re-chunking the same `ParsedDocument` twice, and re-parsing the same file bytes twice, both confirmed byte-identical output). **Went further than "state it's unmeasurable" on the proxy-token-count question**: discovered `voyageai.Client` ships a real local tokenizer (`(...).tokenizer(model).encode_batch(texts)`) that needs no API call — ran it against all 46 chunks produced from the two text-bearing fixtures. Mean proxy/real ratio 0.94 (the char/4 proxy is close to Voyage's real count on average), but individual chunks ranged 0.43x–2.31x, meaning the proxy can be off by more than 2x on any single chunk despite being accurate in aggregate. Computed the worst case against the ceiling: even at the worst measured underestimate factor, `MAX_CHUNK_TOKENS=4000` corresponds to at most ~9,300 real tokens — about 29% of Voyage's actual 32,000 limit, still comfortable margin. Documented this as the basis for concluding FEAT-006 doesn't need its own separate size defense, while explicitly flagging that this conclusion rests on 2 fixtures' worth of measurement and should be re-checked against real production documents if a Voyage rejection is ever actually seen. Logged the `claimed_targets` greedy-first-caption-wins behavior in `.agent/MEMORY.md §Anti-patterns` as an accepted simplification (0 real instances of competing captions observed in `table_heavy.pdf`, the only real multi-caption-per-page data available) rather than a bug to fix speculatively.
**Verification — fixture counts and Tier-2 resolutions confirmed unchanged:** `clean_digital.pdf` 3 chunks, `table_heavy.pdf` 43 chunks (13 explicit / 6 heuristic / 10 uncaptioned, same 6 pairings as before), `scanned.pdf` 2 chunks — **0 chunks actually split on any of the three real fixtures**; the largest real table chunk measured ~418 proxy tokens against the 4,000 ceiling, nowhere close to triggering it. Splitting itself was verified via synthetic oversized inputs only (a 2,000-row table, a 1,000-sentence paragraph — both split correctly, no rows/sentences lost or duplicated, confirmed by counting occurrences across all resulting parts).
**Changed:** `apps/api/services/chunker.py` (size ceiling, splitting, `split_from_element_id`), `apps/api/tests/test_chunker.py` (10 → 21 tests), `.agent/api-docs/voyage.md` (new — Voyage limits + measured proxy-accuracy data), `.agent/MEMORY.md` (new anti-pattern entry), `.agent/FEATURES.md` (FEAT-005 entry updated).
**Impact:** FEAT-006 can build its Voyage embedder wrapper knowing chunker.py's output is bounded well under Voyage's real limits, with actual measured evidence rather than an assumption — and doesn't need to duplicate a size check unless real usage proves otherwise. Full backend suite: 53 passed, 14 skipped (local Postgres not running — unrelated environmental state, not a regression; same 14 skip whenever the local Supabase Docker stack isn't up).
**Rollback:** Revert `apps/api/services/chunker.py` and `apps/api/tests/test_chunker.py` to their pre-follow-up state; remove `.agent/api-docs/voyage.md` if not wanted for other features (FEAT-006 will need it again regardless); revert `.agent/MEMORY.md` and `.agent/FEATURES.md`.

## 2026-07-23 — feature: chunker service, Tier 1 + Tier 2 caption association (FEAT-005)
**Phase:** 1 (Ingestion Pipeline)
**Feature:** FEAT-005
**Decision:** Ran `/test-scaffold FEAT-005` first (4 stubs, correctly scoped). Implemented `Chunker.chunk(ParsedDocument) -> list[Chunk]`: TEXT/HEADING/LIST elements group into running ~500-token chunks (approximated at ~4 chars/token — no tokenizer dependency added just for a budget heuristic; documented as swappable if accuracy becomes a problem), never splitting an individual element's own content across two chunks. TABLE and FIGURE elements always get their own dedicated chunk, mirroring each other structurally. Caption handling is two-tier, per instructions: **Tier 1** consumes what the parser already knows — a table/figure with `associated_caption_ids` populated gets its caption(s) merged directly into its chunk's content (prepended for tables; for figures, the caption becomes the chunk's entire text content since an image can't have text literally prepended into it — the image itself travels separately via `Chunk.image`). **Tier 2** is the proximity heuristic for captions the parser left as `association_method == "none"`: candidate table/figure elements are filtered to the caption's own page and to targets that don't already have a Tier-1 caption (so a heuristic guess never doubles up with a Docling-verified link), then ranked by reading-order distance (primary key) with bbox-center Euclidean distance as a tie-break (secondary key) — literally implementing "same page, adjacent in reading order, nearest by position if multiple candidates." A caption Tier 2 can't place anywhere becomes its own standalone chunk with `association_method="unmatched"`, not silently dropped. Every chunk carries `association_method` (`"explicit"` / `"heuristic"` / `"unmatched"` / `None`) and `merged_caption_ids`, so any chunk's caption provenance is traceable after the fact.
**Measured on `table_heavy.pdf` (29 tables, 19 captions):** 13 explicit (Tier 1), 6 heuristic (Tier 2), 10 tables with no caption at all (neither tier — genuinely uncaptioned in the source, not a failure). **All 6 Tier-2 matches, reported for inspection before marking anything complete, as requested:**

|---|---|---|
| "Table 14: symbols replaced by real text" | chunk 21 (yes/no driving-licence table) | Yes |
| "Table 15: courses offered by Institution X. A = Bachelor..." | chunk 22 (course-code table, A/B/C/D/E values) | Yes |
| "Table 18: accounts, 2011 (£, thousands)" | chunk 25 (table ending in a "Balance ... 30,000" row) | Yes |
| "Table 19: Human Development Index (HDI)" | chunk 27 (table with an "Angola" row, HDI-shaped decimals) | Yes |

All 6 pairings were checked by eye against the actual table content (not just "a match was found") — each caption's stated subject plausibly matches its matched table's visible content. Pinned as exact-ID assertions in `test_tier2_heuristic_resolves_all_six_remaining_captions_in_table_heavy`, so a future change to Docling's output or the heuristic that silently shifts a pairing gets caught by a test, not discovered downstream in FEAT-006's embeddings. While writing tests, found `test_chunker.py` was re-parsing `table_heavy.pdf` from scratch in 5 separate tests (~8 min total) — converted to module-scoped pytest fixtures (`table_heavy_doc`, `clean_digital_doc`, `scanned_doc`), cutting the file's runtime to ~1.7 min. `test_parser.py` has the same repeated-parse pattern but was left untouched — out of scope for this task's file list.

**Impact:** FEAT-006 (Voyage embedder) can now build against real `Chunk` objects — text content, table markdown with captions prepended, and figure images with caption text alongside — instead of raw `ParsedElement`s. The 10 genuinely-uncaptioned tables and the caption-matching provenance (`association_method`) are both preserved through to FEAT-006, so a future "verify our chunks look right" pass has the information to distinguish a confident chunk from a guessed one.

## 2026-07-22 — fix: parser exception coverage + silent-drop visibility (FEAT-004 Codex follow-up)
**Phase:** 1 (Ingestion Pipeline)
**Feature:** FEAT-004
**Decision:** Codex reviewed `parser.py` and found two real gaps. (1) The `try/except` wrapping `Parser.parse()` only covered `converter.convert()`, not the element-iteration loop after it — a failure during `doc.iterate_items()`, provenance access, or bbox extraction would surface as an unwrapped exception instead of `ParseError`. (2) An element with missing provenance (a type we model, e.g. a caption, but with no page/bbox available) was silently dropped via a bare `continue` — no error, no log, no trace it happened. The same silent-drop pattern already existed for figures where `PictureItem.get_image()` returns `None`. Fixed both: the entire iteration loop is now inside the `try`, and the resulting `ParseError` carries `last_page_number` — the last successfully-processed element's page — as best-available context, since the failure may occur before the next element's own provenance is read. Both silent-drop cases now increment a new `ParsedDocument.dropped_elements: int` field and log a `WARN` with what was dropped and why. Deliberately did *not* extend this to labels we don't model at all (`page_header`, `footnote`, `formula`, ...) — that filtering is expected and already documented in a comment; treating it the same as a genuine drop would make `dropped_elements` noise instead of signal. Added a docstring to `ParsedDocument` stating the figure-image ownership contract explicitly: the parser doesn't close `PIL.Image` objects it returns, callers must after persisting them. Tried to reproduce Codex's "truncated PDF" probe with real file corruption (simple truncation, mid-file byte removal at various offsets) to get a permanent regression test from an actual malformed PDF — pdfium turned out to be all-or-nothing about it: truncated files fail outright at `converter.convert()` (already covered by the pre-existing try/except, not the new one), and files corrupted by removing a mid-file byte range are tolerated silently, returning fewer elements with no error at all — never the "convert succeeds, iteration fails" case the new code actually needed to prove. Used a fake converter/document instead for deterministic coverage of that exact path, plus real-file tests for empty-bytes and truncated-bytes input (both legitimate regression tests in their own right, just not exercising the new code path specifically).
**Changed:** `apps/api/services/parser.py` (extended try/except, `dropped_elements` field + WARN logging, `ParsedDocument` docstring), `apps/api/tests/test_parser.py` (7 → 12 tests: empty PDF, truncated PDF, fake mid-iteration failure, fake missing-provenance drop, pinned element-count regression guard), `.agent/FEATURES.md` (FEAT-004 entry updated with the follow-up).
**Impact:** Verified the fix is a no-op on well-formed input before calling this done: all three fixtures re-parsed and produced identical output to before the change (`clean_digital.pdf` 21 elements, `table_heavy.pdf` 66, `scanned.pdf` 2; `dropped_elements: 0` for all three) — pinned as an explicit regression test, not just re-eyeballed. Full parser suite: 7 → 12 tests, all passing (~4.5 min on CPU, up from ~2.5 min — more tests re-parse the same fixtures). Full backend suite: 43 passed. FEAT-005 (chunker) now has a `dropped_elements` signal available if it wants to surface parse completeness to the user, and can rely on `ParseError` actually being the only exception type `Parser.parse()` raises.
**Rollback:** Revert `apps/api/services/parser.py` and `apps/api/tests/test_parser.py` to their pre-follow-up state; revert `.agent/FEATURES.md`.

## 2026-07-22 — fix: live RLS/storage enforcement proven; found and fixed missing table grants (FEAT-001)
**Phase:** 1 (Ingestion Pipeline)
**Feature:** FEAT-001
**Decision:** Codex's review flagged that RLS enforcement had only ever been checked statically (policy presence in the SQL) — never proven against a live database, since `test_migrations.py`'s 14 tests had always skipped (no local Postgres reachable). Set up a real local Supabase instance (`supabase init` + `supabase start` via Docker; first run pulled ~20 images, several minutes) and ran the full migration + test suite against it for real: **14/14 passed, 0 skipped**. Then wrote a live enforcement script exercising four real scenarios over actual HTTP (PostgREST/GoTrue/Storage, no mocks): cross-user `chunks` isolation via two real logged-in users, an authenticated non-owner INSERT attempt, a fully anonymous INSERT attempt, and an authenticated write attempt to the `figures` storage bucket. First run failed immediately — not on RLS, but on a service-role INSERT into `documents` returning `permission denied for table documents`. This blocked *everything*, including `service_role` (its `BYPASSRLS` attribute only bypasses the RLS layer, not the independent GRANT layer). Wrote `apps/api/migrations/20260722_002_grant_table_privileges.sql`, granting exactly what each table's existing policies imply — nothing more. Re-ran the live script: all four checks now pass (see `.agent/GAPS.md` for the exact status codes and response bodies, since two of the four rejections come from the GRANT layer and two from genuine RLS policy firing — worth keeping that distinction visible rather than reporting a flat "4/4 RLS enforced").
**Changed:** `apps/api/migrations/20260722_002_grant_table_privileges.sql` (new), `.agent/SCHEMA.md` (§Migration log entry), `.agent/GAPS.md` (new finding logged under a live-verification section).
**Impact:** **CRITICAL, unresolved on the live project.** This gap almost certainly exists on the live Supabase project (`nbrfjbjjjhawscncshdz`) too — nothing has ever attempted a write against these tables there. FEAT-004 onward (ingestion pipeline) cannot actually persist data against the live project until `20260722_002_grant_table_privileges.sql` is applied there via the dashboard SQL editor, the same way `001` was, and re-verified.
