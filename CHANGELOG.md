## 2026-07-27 — feature: SSE streaming for /query (FEAT-016)
**Phase:** 2 (moved from its original Phase 4 placeholder — see FEATURES.md's Decision)
**Feature:** FEAT-016
**Decision:** Replaced the chat page's staged-loading-text stand-in (`loading-stages.tsx`, built against FEAT-012's real measured 3.4–9.3s latency but driven by a fake `setInterval`, no real backend signal) with real SSE streaming of Gemini's generation tokens via a new `POST /query/stream` route, additive alongside the existing synchronous `/query`. Three design decisions stated explicitly before implementing (see FEATURES.md's FEAT-016 entry for full reasoning): tokens stream progressively (not just stage events); citation markers/verdict styling are held back until verification completes (claim-span extraction needs the full answer text — a hard dependency, not a choice); a separate route, not a mode flag, since `response_model=QueryResponse` and `StreamingResponse` are mutually exclusive in FastAPI.

**Event sequence:** `retrieving -> token* -> verifying -> citations-resolved -> done`, `error` replacing any step from `token` onward and always terminating the stream. Full contract in `API_CONTRACT.md`.

**A real bug found via genuine browser testing that two layers of protocol-level tests both missed:** every blocking call inside the SSE generator (`Verifier.verify_batch` above all) is now wrapped in `asyncio.to_thread(...)`. Calling `verify_batch()` directly (the initial implementation) froze the event loop for its entire real ~8s Gemini-verification duration, which silently prevented uvicorn from flushing the already-yielded `verifying` frame until the next yield — the client received `verifying` and `citations-resolved` simultaneously instead of with the real gap between them, defeating the whole point of a separate event. Both a raw-httpx e2e script and the FastAPI `TestClient`-based unit tests happened to mask this (their own client-side read buffering apparently coalesced the frames identically either way); only a real Playwright browser session against the real dev server, with a temporary client-side event-arrival timestamp log, made it observable. Fixed; re-verified live showing a genuine multi-second `verifying` indicator window.

**Real, honest latency finding, not overclaimed:** streaming's benefit is real but proportional to answer length. A short factual answer streams in only 3 chunks clustered in a ~25ms burst near the end of Gemini's own generation (confirmed this is real Gemini behavior, not a bug, by calling `Generator.generate_stream()` directly with no HTTP/ASGI stack involved) — time-to-first-token (6.6s) barely beats non-streaming's time-to-complete (8.4s). A longer, open-ended answer on the same document streams genuinely progressively — 20 real token events across ~2.0s, first token at 8.09s vs non-streaming's 25.45s — **17.35s earlier visible content**, which is most of this app's real usage pattern per FEAT-012's own quality fixtures.

**Verified:** `test_query_stream.py` re-runs FEAT-011/012's exact citation-safety assertions (supported/partial/unsupported handling, marker-stripping, audit persistence) against the streaming path specifically, plus mid-stream generation-failure and post-generation verification-failure cases (both produce a terminal `error` event, never a hang or a silent partial answer). Auth-over-SSE confirmed live: missing/invalid JWT, non-owned `document_id`, and empty `document_ids` all return a plain JSON error with zero SSE bytes, never a stream that opens and then rejects — `JWTAuthMiddleware` completes its check before `call_next()` structurally, not just by convention. Full backend suite (271 passed, 11 skipped) and a real browser session (real local Supabase Auth sign-in, real ingested document, zero console errors) both re-run clean after the fix.
**Changed:** `apps/api/services/generator.py` (`Generator.generate_stream()`, `GenerateStreamResult`), `apps/api/routes/query.py` (new `POST /query/stream`, `_stream_query_events()`, `post_query()` refactored to share validation helpers — behavior-preserving, 55 existing tests unchanged), `apps/api/tests/test_query_stream.py` (new), `apps/web/lib/api/query.ts` (`askQuestionStream()`), `apps/web/components/chat/loading-stages.tsx` (rebuilt around real SSE state, not a timer), `apps/web/app/(app)/chat/[conversation_id]/page.tsx`, `.agent/API_CONTRACT.md`, `.agent/FEATURES.md`, `.agent/SCOPE.md`.
**Impact:** The 3.4–9.3s `/query` wait (FEAT-012's own measured latency) now shows real, growing content almost immediately for longer answers instead of a generic loading animation — directly closes the gap `loading-stages.tsx`'s own code comment named as this project's last deferred Phase 4 item. Citation-verification safety is unchanged: no new path exists where an unverified claim can render as verified.
**Rollback:** Revert all `Changed` files above; `/query` itself is untouched, so no data/schema rollback is needed.

## 2026-07-27 — feature: DOCX/PPTX/HTML ingestion (FEAT-020)
**Phase:** 4 (Polish)
**Feature:** FEAT-020
**Decision:** Extended ingestion beyond PDF to DOCX, PPTX, and HTML, verified against real fixtures per format before any code was written — not assumed that "Docling supports it" means this codebase handles it correctly. A real, per-format Docling investigation (table.docx, slides.pptx, page.html — all new real fixtures, not hand-waved) found the three formats behave very differently from PDF and from each other, driving every design decision below.

**Real per-format findings, the core of this feature:** DOCX and HTML never carry `item.prov` at all — no page number, no bbox, for any element, ever (confirmed live, not a rare anomaly). PPTX carries real provenance exactly like PDF, with `page_no` genuinely the 1-indexed slide number. Figure extraction works with zero configuration for DOCX/PPTX (real embedded image objects, unlike a PDF page needing render/crop) but is confirmed broken for HTML (`get_image()` returns `None` even though a `picture` element exists). FEAT-004's Tier 1 caption-linking does not function for DOCX at all (even Word's native "Caption" paragraph style comes through as plain text, never `DocItemLabel.CAPTION`); it does work for HTML, but only via an `<img>`'s `alt` attribute — moot since HTML figures don't resolve anyway.

**`page_number` design fork (resolved explicitly before implementing, per the task's own requirement):** kept `chunks.page_number NOT NULL` — no migration. DOCX/HTML get a fixed sentinel (`1`, honest "no location available," not fabricated). PPTX needed zero special-casing — its real slide index flows through the exact same extraction path PDF already used. Documented in `.agent/SCHEMA.md`/`.agent/API_CONTRACT.md`, including an explicitly-flagged, not-fixed frontend gap: `source-panel.tsx` hardcodes "PAGE N" with no format awareness, so DOCX/HTML citations will show "PAGE 1" and PPTX citations "PAGE N" where "SLIDE N" would be accurate.

**`do_ocr`/`generate_picture_images`/`generate_page_images` confirmed genuinely inapplicable, not just unneeded:** these are `PdfPipelineOptions`-only fields. DOCX/PPTX/HTML all use `SimplePipeline`/`ConvertPipelineOptions` (confirmed against the installed Docling source), which has no such fields at all. Same investigation confirmed FEAT-017's OCR fallback chain is already, correctly, a structural no-op for all three new formats — `doc.pages` is empty for DOCX/HTML and `page.image` is always `None` for PPTX, so the existing fallback loop simply never has anything to work with, no explicit exclusion needed.

**A real chunker.py bug found via the real end-to-end test, exactly why the task demanded full-pipeline testing over parser unit tests alone:** the first real PPTX e2e run answered a question correctly but cited page 1 for content that actually lives on slide 2. Root cause: `Chunker`'s text-grouping never flushed on a `page_number` change, and `build_chunk_rows` stores `min(chunk.page_numbers)` — a chunk spanning two slides silently reported only the first. Fixed by treating a page/slide change as a flush boundary, applied uniformly (not PPTX-specific, since it's arguably the more correct default for PDF too) — confirmed zero impact on existing PDF fixtures' chunk counts (table_heavy.pdf still exactly 43).

**Content-sniffing correction, found mid-task:** initial design assumed the filename extension alone drives Docling's format detection. Reading Docling's real `_guess_format()` source and testing directly showed real magic-byte sniffing takes priority for PDF/DOCX/PPTX — confirmed live these three are correctly detected even given a deliberately wrong extension. HTML is the one real exception: a `.pdf` extension confidently short-circuits before HTML's low-priority content-sniffing fallback ever runs, so real HTML content given a `.pdf` name genuinely fails with a real `ParseError`. `Parser.parse()` still gained a `filename` parameter for this reason — `routes/ingest.py` always passes the real uploaded filename, so production never hits this failure mode.

**Real end-to-end results, through the actual `/ingest` + `/query` HTTP endpoints, real Docling+Voyage+Gemini, no fakes:** `table.docx` ("What was Q3 2026 revenue?") → *"In Q3 2026, the revenue was $1,410,000 (USD) [1][2]."*, citation page 1 (correct). `slides.pptx` ("What was the customer count in Q3 2026?") → *"In Q3 2026, the customer count grew to 5,200 [1]."*, citation page 2 (correct, after the chunker fix). `page.html` ("What was Q3 2026 revenue?") → *"Q3 2026 revenue was $1,410,000 [1], [2]."*, citation page 1 (correct).
**Verification:** `test_parser.py` gained 14 new tests (per-format element types/provenance/bbox/figures, content-sniffing robustness including the HTML exception, PDF regression guard). `test_chunker.py` gained 2 (page-boundary flush, single-page unaffected). New `tests/e2e/test_format_ingest_e2e.py` (gated `RUN_FORMAT_INGEST_E2E_TEST=1`) proves all 3 formats through the real HTTP endpoints. Full backend suite re-run for final regression confirmation.
**Changed:** `apps/api/services/parser.py` (`allowed_formats`, `_FORMATS_WITHOUT_PROVENANCE`, `Parser.parse()` gained `filename=`), `apps/api/services/chunker.py` (page-boundary flush), `apps/api/routes/ingest.py` (`SUPPORTED_MIME_TYPES` extended, real filename passed through), `apps/api/tests/fixtures/{table.docx,slides.pptx,page.html}` (new), `apps/api/tests/test_parser.py` + `test_chunker.py` (new tests), `apps/api/tests/e2e/test_format_ingest_e2e.py` (new), `apps/api/tests/conftest.py` (`FakeParser.parse()` accepts `filename=`), `.agent/SCHEMA.md`, `.agent/API_CONTRACT.md`, `.agent/SCOPE.md`.
**Impact:** Users can now upload and query DOCX, PPTX, and HTML documents alongside PDF, with citation quality proven real per format. PDF behavior is unchanged (confirmed via full regression re-run).
**Rollback:** Revert `parser.py`/`chunker.py`/`routes/ingest.py`/test files. No schema/migration changes (page_number stayed `NOT NULL`), no new env var.

## 2026-07-27 — feature: conversation memory in Generator's prompt (FEAT-019)
**Phase:** 2 (Retrieval/Generation)
**Feature:** FEAT-019 (this number was already reserved in FEATURES.md's Phase 4 placeholder list — confirmed by reading the file first, not assumed free; also caught that FEAT-018, reserved for the reranker step, had already been built but mislabeled as a FEAT-009 follow-up — noted there, not silently fixed retroactively since CHANGELOG.md is append-only)
**Decision:** Minimal memory: prior Q&A pairs fold into `Generator`'s prompt so a follow-up like "how does that compare to X?" resolves correctly in the ANSWER. Retrieval itself is unchanged — still searches on the raw current-turn question alone, no query rewriting. A deliberate scope decision, matching the "ship minimal, measure before adding speculative complexity" pattern reranking's rollout established (`.agent/MEMORY.md`, 2026-07-27). Known, explicitly stated limitation: a follow-up whose wording alone wouldn't retrieve well (relies entirely on unstated context) may retrieve poorly even though `Generator` has the context to answer well once the right chunks are found.

**Bounded window:** `MAX_HISTORY_TURNS = 5` (10 messages) — real justification, not an arbitrary number: ordinary follow-up ambiguity resolves against the immediately preceding turn or two in practice; 5 gives generous margin without unbounded prompt growth. Fetched via `db.queries.list_messages_for_conversation()`, reused (not duplicated) from FEAT-026 — the only change is a new optional `limit` param, which `GET /conversations/{id}/messages` doesn't pass, so its own behavior is completely unaffected.

**A real bug found and fixed while building the bounded fetch:** the first implementation bounded the fetch via `ORDER BY created_at DESC LIMIT N` + reverse-in-Python, to avoid a full scan for long conversations. This silently swaps a turn's user/assistant messages whenever they share an identical `created_at` — which is *every turn*, since both insert inside the same `create_query_turn()` transaction and Postgres's `now()` is transaction-start time, not per-statement. A real test (`test_conversation_history_with_limit_preserves_user_then_assistant_order_within_a_turn`) caught this before it ever reached a real conversation. Fixed by reusing the exact already-proven `ORDER BY created_at ASC` query unconditionally and slicing the last N in Python — full-conversation fetch (a cheap, indexed scan on `conversation_id`) accepted as the tradeoff over the correctness risk.

**Citation numbering across turns confirmed unaffected, two ways:** a prior turn's `[N]` markers are stripped entirely before being folded into history text (`_strip_citation_markers`), and `_parse_citations()` only ever scans the model's own freshly-generated answer text, never the prompt — tested directly by planting marker-shaped text (`[1]`, `[2]`, `[9]`, `[99]`) inside fake history content and confirming none of it leaks into the current turn's `cited_indices`/`hallucinated_markers`.

**Multi-tenant isolation re-confirmed at this new surface, not assumed inherited:** the new `limit=` branch of `list_messages_for_conversation()` is called directly with a different real user's id against a conversation they don't own — confirmed empty, with a positive control proving the emptiness is real scoping.

**Real two-turn conversation, `table_heavy.pdf`, real Docling+Voyage+Gemini throughout (no dependency overrides):** Turn 1 ("What is Angola's Human Development Index value in 2010?") → *"According to Table 19, Angola's Human Development Index (HDI) value in 2010 is 4.42 [1]."* (3762ms). Turn 2 ("How does that compare to the year 2000?") → *"In the year 2000, Angola's Human Development Index (HDI) value was 4.42 [4]. Compared to the 2010 value of 4.42, Angola's HDI value remained unchanged [4]."* (4674ms) — correctly resolves "that"/"the year 2000" using turn 1's context and correctly reports the real data (Angola's HDI is genuinely 4.42 in both columns).

**Real latency measurement, isolating history's own effect:** same question/chunks, `Generator.generate()` called directly with `history=None` vs real history, 3 ABBA-counterbalanced trials (order alternates each trial to rule out a call-position confound — an initial fixed-order measurement showed the same surprising direction even more starkly, which is what prompted re-measuring properly). Result: **without history mean 7213.7ms (4763.2–8593.3ms) vs with history mean 3606.9ms (3283.9–3799.4ms)** — history made generation *faster*, not slower, reproduced across both the fixed-order and counterbalanced measurements. Most likely mechanism: with context, the model answers directly and concisely; without it, it likely has to hedge or infer the ambiguous referent, producing a longer answer — output token count, not prompt size, dominates real generation latency. Not fully instrumented to confirm via output token counts, flagged as the likely explanation rather than overclaimed. No update to the ~4-8.3s end-to-end latency budget is warranted — the real measured effect was neutral-to-positive, not an increase.

**Verification:** `test_generator.py` gained 4 tests (history folds in correctly, no-history is a byte-identical no-op, historical markers are stripped, new-turn citation numbering is unaffected by marker-shaped history text). `test_query.py` gained 6 tests (empty history on first turn, real history on second turn, bounded window truncation, the user/assistant tie-break regression test, isolation at the new `limit=` path, and the real gated quality+latency test). Full `test_query.py` + `test_conversations.py` + `test_generator.py`: 61 passed, 2 skipped (gated real tests).
**Changed:** `apps/api/services/generator.py` (`Generator.generate()` gained `history=`, new `_build_history_parts`/`_strip_citation_markers`/`_HISTORY_HEADER`, `SYSTEM_INSTRUCTION` extended), `apps/api/routes/query.py` (`MAX_HISTORY_TURNS`, history fetch + pass-through), `apps/api/db/queries.py` (`list_messages_for_conversation()` gained `limit=`), `apps/api/tests/test_generator.py` (4 new tests), `apps/api/tests/test_query.py` (6 new tests, `FakeGenerator`/`FakeGeneratorRaising` updated to accept `history=`), `apps/api/tests/test_conversations.py` (`FakeGenerator` updated to accept `history=`), `.agent/FEATURES.md` (new FEAT-019 entry, FEAT-018/FEAT-019 placeholder-list correction).
**Impact:** `/query` calls with a `conversation_id` now carry real conversational context into generation, with zero behavior change for calls without one. `GET /conversations/{id}/messages` (FEAT-026) is completely unaffected — it never passes the new `limit` param.
**Rollback:** Revert all `Changed` files above. No schema/migration changes, no new env var.

## 2026-07-27 — fix: Embedder/Retriever eager-construction crash on missing VOYAGE_API_KEY
**Phase:** 1/2 (FEAT-006/FEAT-009)
**Feature:** FEAT-006 (follow-up), flagged during FEAT-009's rerank follow-up the same day
**Decision:** Same bug class FEAT-017's audit found and fixed in `GeminiOcrClient`/`OcrSpaceClient`: bare `voyageai.Client()` construction crashes immediately with `AuthenticationError` if `VOYAGE_API_KEY` is absent, rather than failing only on first actual use. `Embedder.__init__` built its client eagerly since FEAT-006 — meaning a bare `Embedder()`, and by extension `Retriever()` (which builds a default `Embedder()`), crashed in any environment missing the key, even for callers that never call `embed()`/`embed_query()`. Applied the same lazy-construction pattern already established for the OCR tiers and for FEAT-009's own `Reranker`: the real client resolves on first actual call, not at `__init__`.

**A second, related gap found and fixed while closing the first:** `embed()`'s batch loop calls `_get_tokenizer()` before its own try/except (the tokenizer is needed to decide batch boundaries), so a missing key surfacing there previously escaped as a raw `voyageai.error.AuthenticationError` rather than `EmbedError` — inconsistent with `EmbedError`'s own documented contract ("Non-transient embedding failure — auth, invalid request, ..."). Fixed by catching `VoyageError` inside `_get_tokenizer()` itself, so both `embed()` and `embed_query()` now fail identically and cleanly regardless of which internal step first touches the client.

## 2026-07-26 — feature: OCR fallback via Gemini Flash for low-yield scanned pages (FEAT-017)

Implemented without that exemption: `scanned.pdf`'s actual last page (page 3) is itself unread scanned content, not a genuine blank page. ## 2026-07-24 — feature: Citation verifier, Gemini Flash-Lite LLM-as-judge (FEAT-011)
**Phase:** 2 (Retrieval + Generation)
**Feature:** FEAT-011
**Decision:** The adversarial safety layer for the whole generation pipeline — FEAT-010 proved the generator cites the position it claims to; this checks whether what it *says* about that position is actually true. `Verifier.verify(claim_text, chunk: GeneratorChunk) -> Verdict` deliberately reuses FEAT-010's `GeneratorChunk` rather than introducing a third near-identical chunk type — by verification time, FEAT-012 already has `GeneratorChunk`s built (images already fetched) for the `generate()` call, so reusing them avoids a redundant Storage round-trip. Same scope boundary as FEAT-010: `verify()` takes already-resolved `(claim_text, chunk)` pairs and does no `[N]`-to-chunk resolution itself — that's `/query`'s job, now written into FEAT-012's acceptance criteria alongside a precise verdict-to-UI-treatment note (`supported` → normal, `partial` → kept with a warning icon, `unsupported` → dropped — corrected once already this session after an early draft of that note wrongly said `partial` gets dropped too, caught against `.agent/ARCHITECTURE.md`'s verify flow before it shipped).

**Structured output instead of free-text parsing — a direct lesson from FEAT-010's own audit, applied before shipping rather than after:** FEAT-010's `[N]`-marker regex needed three separate rounds of live fixes (grouped brackets, delimiters, sign handling) because it parsed free text. `Verifier` uses the SDK's `response_schema`/`response_mime_type="application/json"` (a pydantic model, verified against installed SDK source) instead, closing that whole failure class here rather than re-discovering it through a second round of bugs. A caller that only reads `.verdict` and never checks `.error` still gets the safe outcome by construction — the guarantee lives in `Verifier`, not in a convention `/query` has to remember to uphold (the same "invariant enforced by the thing that needs it true" lesson as FEAT-007/009's audits).

**Batching:** `Verifier.verify_batch(pairs)` runs one Gemini call per `(claim_text, chunk)` pair concurrently via `ThreadPoolExecutor` — same shape as FEAT-009's parallel vector/FTS search — preserving input order regardless of completion order, and confirmed that one failing pair in a batch doesn't contaminate the others' results.

**Adversarial fixture, real content not synthetic strings — item 4's explicit requirement:** real Docling-parsed `table_heavy.pdf` content (no Voyage/embeddings needed, since verification doesn't retrieve), the real HDI table row (Angola, 4.42) reused from FEAT-009/010. The citation FEAT-010 already proved was *positionally* correct (`cited_indices=[1]`, real HDI chunk) was independently verified as `supported` with an exact real quote — confirming "positionally correct" and "factually correct" are the same thing here in practice, not merely assumed to be. 438 input tokens, 41 output tokens, 1564ms.

**Verification:** 14 fast/mocked tests (verdict/quote handling, defensive quote-nulling on model deviation, multimodal image passthrough, batching + concurrency + order-preservation + isolation-of-one-failing-pair, and 4 tests specifically proving fail-safe behavior) + 4 real/gated tests (single-claim smoke test, real-invalid-key fail-safe proof, adversarial fixture, compound end-to-end) in `apps/api/tests/test_verifier.py`. **Changed:** `apps/api/services/verifier.py` (new), `apps/api/tests/test_verifier.py` (new, 18 tests), `.agent/api-docs/gemini.md` (structured-output section added), `.agent/FEATURES.md` (FEAT-011 → complete; FEAT-012 gets a new `Verifier`-usage acceptance criterion, corrected once before shipping per the partial-vs-unsupported catch above).

## 2026-07-24 — feature: Retriever service, hybrid search + RRF (FEAT-009)
**Phase:** 2 (Retrieval + Generation)
**Feature:** FEAT-009
**Decision:** First Phase 2 feature, and a different verification shape from everything before it: Phase 1's features needed to prove correctness and safety (does it run, is it isolated, does it not corrupt data); this one additionally needs to prove *quality* — does hybrid search actually find the right content for a real question, which has no prior precedent in this project to lean on.

**Why a new migration, not just `retriever.py`:** neither pgvector cosine ranking (`embedding <=> query_embedding`) nor Postgres FTS ranking (`ts_rank`) is expressible through PostgREST's REST query builder — `.select()`/`.order()` only support plain column comparisons and a fixed operator set, not arbitrary SQL expressions in `ORDER BY`. The standard, documented way to do this through Supabase's REST layer is a Postgres function called via `client.rpc(...)`. Added `apps/api/migrations/20260724_001_hybrid_search_functions.sql` — `match_chunks_by_vector` and `match_chunks_by_fts`, both taking `match_user_id`/`match_document_ids` as explicit function parameters and filtering on them directly in the `WHERE` clause (per this task's explicit requirement: scoped explicitly, not relying on RLS alone — these functions are only ever called with the service-role client, which bypasses RLS entirely, so the explicit filter is the actual tenant boundary, matching FEAT-007/008's established pattern). `EXECUTE` revoked from `PUBLIC` (Postgres's default for new functions) and granted only to `service_role`. Applied and verified against the real local Supabase stack before any Python code was written — confirmed vector-distance ordering, FTS ranking, and user_id scoping all work correctly via a throwaway probe script, deleted after use.

**Why `embedder.py` also changed:** Voyage's embeddings are asymmetric — query-side and document-side calls use different internal prefixes for better retrieval quality (documented in `.agent/api-docs/voyage.md` since FEAT-006, flagged there at the time as "a separate concern... not addressed here"). `Embedder.embed()` hardcodes `input_type="document"` for ingestion; embedding a bare query string through it would silently degrade retrieval quality. Added `Embedder.embed_query(text) -> Vector`, a small, additive, `input_type="query"` counterpart — `embed()`'s own signature and behavior are unchanged, so this doesn't touch FEAT-006/007's existing tested behavior.

**RRF, and the naming confusion this task explicitly called out:** `RRF_K = 60` (the fusion constant, dampens the influence of low ranks in `1/(RRF_K + rank)`) and `DEFAULT_K = 8` (the retrieval count, per `.agent/SCOPE.md`'s Phase 2 spec) are two completely different numbers that happen to share a letter — confusing them produces a plausible-looking but wrong result with no error to catch it. **Parallelism — the one place in this codebase with real thread-level concurrency:** vector search and FTS search are independent read-only queries with no dependency on each other's results, so `Retriever.retrieve()` runs them via a `ThreadPoolExecutor`, proven with real wall-clock timing (two 0.4s-sleeping fake search methods complete in ~0.4s total, not ~0.8s) rather than just asserting both got called. ## 2026-07-23 — fix: **SECURITY** — path traversal in `/ingest`'s storage_path allowed reading another tenant's file (FEAT-007)
**Phase:** 1 (Ingestion Pipeline)
**Feature:** FEAT-007
**Severity:** High — confirmed exploitable, not theoretical. Any authenticated user could get the ingest pipeline to download, parse, chunk, and embed another user's document into their own `chunks` (a real cross-tenant content leak), by supplying a crafted `storage_path` in an otherwise-normal `POST /ingest` request. No special access or timing was required — one JSON body field.
**Decision:** Found via a proactive self-audit (run ahead of a separate, parallel Codex security/perf review specifically because it was cheap to check and would have been flagged either way — not deferred, fixed immediately ahead of everything else per explicit instruction, blocking FEAT-008 and the broader review). The root cause: `storage_path` ownership was checked with `storage_path.startswith(f"uploads/{user_id}/")` — a literal string comparison with no understanding of `".."` path semantics. `"uploads/{attacker}/../{victim}/file.pdf"` satisfies that check (it genuinely starts with the attacker's own prefix as a string) while Supabase Storage's own server resolves the `".."` when actually fetching the object — confirmed two independent ways against the real local Storage stack: via the `storage3` SDK (the exact call `run_ingest_pipeline()` makes) and via a raw HTTP request straight to the Storage REST API, bypassing our SDK entirely. Both returned the victim's real file content. Because `run_ingest_pipeline()` downloads using the **service-role client**, which bypasses RLS entirely, the string check was the *only* authorization gate standing between an attacker-controlled path and a fully-privileged file read.
**First fix attempt was ALSO proven exploitable — this matters, don't skip it:** the initially "obviously correct" fix (reject any raw `".."` path segment, require `posixpath.normpath(path) == path`) was tested live before being trusted, and failed: a percent-encoded variant, `"uploads/{attacker}/%2e%2e%2f{victim}/file.pdf"`, contains no literal `".."` and is already normpath-canonical, yet still resolved to the victim's file — some layer in the request chain decodes `%2e%2e` back to `..` before our check ever sees it (standard, spec-compliant behavior per RFC 3986, not a bug in Supabase). Enumerating every spelling of `".."` is a losing game, so the final fix does not attempt it: `validate_storage_path()` (new, in `apps/api/routes/ingest.py`) checks the trusted `"uploads/{user_id}/"` prefix (built server-side from the verified JWT, never from client input), then requires everything after it to match a narrow character whitelist (`^[A-Za-z0-9._-]+$`) with **no path-separator character — literal or encoded — possible by construction**. This closes the entire bypass class (known variants and not-yet-invented ones) rather than pattern-matching against known-dangerous spellings. The literal-`".."` and normpath-equality checks from the first attempt are kept as a cheap extra layer, not as the primary defense.
**Single shared function, both call sites:** `validate_storage_path()` is called from both `post_ingest()` (the synchronous 403 path, before any document row is created) and `run_ingest_pipeline()` itself (the defense-in-depth check added in FEAT-007's prior Codex-review follow-up) — one implementation, not two that could drift, per this task's explicit requirement.
**Verification — proven at four levels, not just unit tests:** (1) a fast unit-level matrix directly against `validate_storage_path()` — literal traversal, percent-encoded traversal, mixed literal+encoded, absolute path, non-canonical double-slash, and a normal valid path (must still pass) — 8 cases, all correct; (2) route-level tests (`test_ingest_route_rejects_path_traversal_storage_path`, parametrized over all three traversal spellings) confirming `403` and zero document rows created; (3) pipeline-level tests calling `run_ingest_pipeline()` directly, bypassing the route, confirming `status='failed'` and zero chunk rows; (4) **the literal live proof-of-concept re-run in reverse**, per this task's explicit instruction not to trust the unit tests alone — a real user A uploads a real file with real, identifiable secret content, a real unrelated user B attempts the exact two exploit strings that previously succeeded against the live stack, both now blocked with `403` before any Storage call is made, and a standalone confirmation script (mirroring the original recon probe exactly) shows `validate_storage_path()` raising before `client.storage.download()` is ever reached for either variant. `tests/test_ingest.py` grew from 10 to 23 tests. Full backend suite re-run after the fix: **112 passed, 2 skipped** (the two intentionally-gated real-API/e2e tests) — no regressions.
**Changed:** `apps/api/routes/ingest.py` (`validate_storage_path()`, `StoragePathError`, `_SAFE_FILENAME`; replaces the old `_storage_path_belongs_to_user`/`IngestInvariantError`; both `post_ingest()` and `run_ingest_pipeline()` now call the one shared function), `apps/api/tests/test_ingest.py` (10 → 23 tests), `.agent/MEMORY.md` (new `§Anti-patterns` entry: `startswith()` is not a safe authorization boundary for path-like input — distinct lesson from the two "invariant not enforced" findings already logged, since the failure mode here is a different kind: the check ran in the right place every time and was still wrong).
**Impact:** The confirmed cross-tenant file-read via `/ingest` is closed. `run_ingest_pipeline()`'s only remaining trust in `storage_path` is that it's a `{uuid}.{ext}`-shaped string directly under the caller's own trusted prefix — nothing else about its content can route the pipeline anywhere else, encoded or not. This was fixed ahead of FEAT-008 and the parallel Codex review, per explicit instruction that this class of finding blocks everything else until closed, tested, and the live proof-of-concept confirmed dead — not batched with other findings for a single triage pass.
**Rollback:** Revert `apps/api/routes/ingest.py` and `apps/api/tests/test_ingest.py` to their pre-fix state; revert `.agent/MEMORY.md`. Not recommended — this would reopen a confirmed, live cross-tenant vulnerability.

## 2026-07-23 — fix: ingest pipeline invariant enforcement + failure-path hardening (FEAT-007 Codex follow-up)
**Phase:** 1 (Ingestion Pipeline)
**Feature:** FEAT-007
**Decision:** Codex review of `ingest.py` found one real structural gap and confirmed a previously-flagged risk as real-but-deliberately-deferred. **The gap:** `run_ingest_pipeline()`'s correctness depends on `storage_path` actually belonging to `user_id`, and on `get_service_role_client()`/`Parser()`/`Chunker()`/`Embedder()` constructing successfully — but both were only ever true because the function's one caller (`post_ingest`) happened to check/succeed first. The function itself trusted both unconditionally, and dependency construction ran *before* the `try` block, so a construction failure had no handler to reach at all. Fixed by moving the storage_path/user_id check inside `run_ingest_pipeline()` itself (raises a new `IngestInvariantError`, caught by the same except block as everything else) and moving all four dependency-construction calls inside the `try`. Rewrote the except block as `_fail_document()`: if `client` never got constructed, there's nothing to write with, so it logs at ERROR and stops (a known, visible limit, not a silent swallow); otherwise `delete_chunks_for_document` and `mark_failed` are each attempted independently in their own best-effort try, so one failing doesn't skip the other, and either failing logs at ERROR with the original error preserved in the message rather than leaving the document stuck at an intermediate status with zero trace. Three new tests prove each fix directly rather than by inspection: `test_run_ingest_pipeline_refuses_mismatched_user_id_and_storage_path` calls the function directly with a mismatched path, bypassing the route entirely, and confirms it refuses (status `failed`, zero chunk rows) using fakes that would have "succeeded" if the check hadn't fired; `test_dependency_construction_failure_marks_document_failed` patches `Parser` to raise on construction (the real default-construction path, not an injected fake) and confirms the document ends up `failed` with the construction error as its message, not stuck at `uploaded`; `test_cleanup_failure_is_logged_and_does_not_crash_pipeline` uses an always-failing fake client so both the main pipeline call and its own cleanup calls fail, and confirms `run_ingest_pipeline()` still returns cleanly (no unhandled exception inside what would be a FastAPI `BackgroundTask`) while both cleanup failures are logged at ERROR with the document id present.
**Confirmed-but-deferred: background-task durability.** Codex confirmed the durability gap flagged as a risk during FEAT-007's original implementation is real — FastAPI `BackgroundTasks` has no timeout, dead-letter, or crash-recovery mechanism, so a genuinely hung or crashed task is invisible beyond ordinary log output. Per this task's explicit instruction, no durable job queue or retry mechanism was built here — that's Phase 5 (deploy architecture) territory, not something to patch incrementally into a `BackgroundTasks`-based v1. Logged as an explicit out-of-scope entry in `.agent/SCOPE.md` Phase 1 rather than left as an implicit, undocumented limitation.
**General lesson logged, not just this instance:** `.agent/MEMORY.md §Anti-patterns` gets a new entry — "no current caller violates an invariant" is not the same claim as "the invariant is enforced." This project has now hit this shape of gap more than once (FEAT-003's circular-JWT-verification bug is a different flavor of the same root issue: a check that technically passes without proving what it claims to). Logged as a general review lens to apply proactively — when a function's correctness depends on a precondition, ask whether the function itself refuses to proceed without it, not just whether every caller today happens to uphold it.
**Verification:** `tests/test_ingest.py` grew from 7 to 10 tests, all passing against the real local Supabase stack. Full backend suite re-run after these changes: **99 passed, 2 skipped** (the two intentionally-gated real-API/e2e tests) — no regressions.
**Changed:** `apps/api/routes/ingest.py` (`IngestInvariantError`, `_fail_document`, invariant check + dependency construction moved inside `try`), `apps/api/tests/test_ingest.py` (7 → 10 tests), `.agent/SCOPE.md` (new Phase 1 out-of-scope entry: background-task durability deferred to Phase 5), `.agent/MEMORY.md` (new §Anti-patterns entry), `.agent/FEATURES.md` (FEAT-007 entry updated).
**Impact:** `run_ingest_pipeline()` is now safe to call from a future second caller (or a future retry/queue mechanism, if Phase 5 adds one) without silently depending on that caller re-implementing checks the original route happened to do first. No behavior change for the existing `/ingest` → `post_ingest` → `run_ingest_pipeline` path — every existing test from the original FEAT-007 pass still passes unchanged.

## 2026-07-23 — feature: `/ingest` endpoint, full pipeline wiring (FEAT-007)
**Phase:** 1 (Ingestion Pipeline)
**Feature:** FEAT-007
**Decision:** This is the first place FEAT-001/003/004/005/006 meet in one real path — a document uploaded to Storage, authenticated, parsed, chunked, embedded, and persisted, scoped by a real user. `POST /ingest` validates `storage_path` starts with `uploads/{jwt.user_id}/` before anything else (403 otherwise, matching API_CONTRACT.md's stated ordering), rejects non-PDF `mime_type` (422 — Phase 1 is PDF-only per SCOPE.md), creates a `documents` row (`status='uploaded'` by DB default), and schedules `run_ingest_pipeline` as a FastAPI `BackgroundTask` before returning `202`. ## 2026-07-23 — fix: embedder cardinality check + real-tokenizer batching (FEAT-006 Codex follow-up)
**Phase:** 1 (Ingestion Pipeline)
**Feature:** FEAT-006
**Decision:** A Codex review of `embedder.py` found one real bug and one real gap. **Bug:** nothing checked that the number of embeddings Voyage returned matched the number of inputs sent — demonstrated concretely (5 chunks submitted, 4 vectors returned, no error raised, caller would silently receive a misaligned `list[Vector]`). Fixed by asserting `len(result.embeddings) == len(batch)` immediately after each batch call, before extending the accumulated vector list; a mismatch raises `EmbedError` with the batch's `chunk_index` values and the expected-vs-actual counts, and returns nothing (not a partial list) — this fires per-batch, so a mismatch on a later batch in a multi-batch `embed()` call still aborts cleanly rather than returning a partial success. The original `FakeVoyageClient` test double returned an *identical* fake vector for every input regardless of order or count — a double shaped that way could never have caught this bug even by accident, since count-equality alone (which it did happen to preserve) says nothing about correspondence. Rewrote it to return distinct, index-derived vectors per input, and added `test_each_chunk_maps_to_its_own_distinct_vector` — the test that would have caught the original bug directly, asserting each chunk's vector is genuinely distinct and in input order, not just counting outputs. **Gap:** the 320,000-token batch-splitting limit was enforced against `chunker.py`'s char/4 text-token proxy, the same proxy FEAT-005 measured to be off by up to 2.31x on any single chunk — against a limit with only ~12.5% headroom at the old 280,000-token safety budget, that's thinner margin than the ~29%-of-limit-used (~71% margin) FEAT-005 accepted for its own analogous per-chunk ceiling. Rather than just widening the margin further, replaced the proxy with Voyage's own real local tokenizer for the text portion — `voyageai.Client.tokenizer(MODEL)`, the same one FEAT-005 used to *measure* the proxy's error, confirmed (re-verified live this round) to still load and run fully offline for `voyage-multimodal-3.5` specifically, no API call needed beyond a one-time cached Hugging Face download. The image-token portion is unchanged (Voyage's own documented pixel/560 formula, not an estimate — no proxy error to fix there).
